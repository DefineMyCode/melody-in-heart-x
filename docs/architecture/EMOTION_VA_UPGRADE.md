# 情绪 V/A 语义改造方案

> 日期：2026-10-24 · 状态：**已落地**（A/B 于 2026-10-24，C 于 2026-10-25）
> 依据：Redmi 23113RKC6C 上 1095 首曲库的**零人工标注**诊断（`tools/emotion_diag.py`）
> 前置：诊断脚本已入库（`d927f82`）；`userTagsEdited` 采集改造已先行落地（DB v12）
> **最终验收与锚点重标定结果见 §11**（全库真值，1095 首）

## 0. 一句话

把 **arousal** 从"VA 头回归出的曲风代理"换成**直接算的响度包络**（物理定义，定义即准）；
把 **valence** 从"未经标定的回归输出"换成**经零点/斜率标定的输出**。

> **模拟结论（2026-10-24，见 §10）**：
> **A 是必需的**——它是唯一能救「燃」「静谧」的一步（valence 标定后「燃」只剩
> 2.0% 的歌，换成真实响度后回到 24.6%）。
> **B 是有益的**——V 均值 0.264→0.017，词条极差 6.03×→2.71×，半曲一致性 48.5%→62.3%。
> **C（锚点重标定）当时判定"不必做"**——依据是 69 首样本的离线模拟。
>
> ⚠️ **这条判断在 2026-10-25 被全库真值推翻**：A/B 改坐标系后锚点必须跟着搬，
> 不搬就会语义崩坏（「神圣」独占 30.6% 的 top1、「燃」掉到 46 首）。
> C 已按 §11.4 的流程在全库 1095 首上重做完毕。

**参数定稿**：
A = `-30..-5 dBFS → [-1,1]` · B = `(v-0.25)/0.85` · C = **按全库真值重标定**（见 §11.5）

| Bootstrap top1 稳定率 | 均值 **81.2%**，中位 87%（<30% 的歌 0 首） | 词条是稳健属性，非掷骰子 |

| 艺人级 ICC | valence **+0.661** / arousal **+0.671** | **2/3 方差由"谁唱的"解释**（音色主导） |

问题出在**语义**与**标定**：arousal 测的是曲风不是能量，valence 有正偏，锚点按旧假设定的没跟上。

## 3. 方案 A：arousal → 响度包络

### 3.1 语义定义

```
arousal := 该时刻的响度（dBFS）经固定映射后的值 ∈ [-1, 1]
```

- **绝对**能量：整曲都很响 → 整曲投"燃"；最响那 20 秒 → "高潮"落点
- 不再是"这首歌像不像电子乐"

### 3.2 实现位置（零额外解码成本）

`EmotionAnalyzer` 解码链已握有全部 PCM，`resampleTo16k()` 之后就是 16k mono `FloatArray`：

```
解码 → ShortAccum → resampleTo16k → FloatArray(16k)
                                     ├─→ 切 5s 窗 → RMS → dB → arousal   ← 新增，纯本地算
                                     └─→ 切 16384 帧 → YAMNet → VA 头 → valence
```

不碰 YAMNet、不碰模型权重、不增加解码开销。

### 3.3 映射函数

```
rms      = sqrt(mean(x²))                    // 窗内 16k 样本
db       = 20 * log10(rms + 1e-6)             // ≈ -120..0 dB
arousal  = clamp((db - DB_FLOOR) / (DB_CEIL - DB_FLOOR) * 2 - 1, -1, 1)
```

`DB_FLOOR` / `DB_CEIL` 三个候选：

| 方案 | 取值 | 优点 | 代价 |
|---|---|---|---|
| **A1 物理固定** | −60 dB / 0 dB | 绝对、可解释、不随曲库变 | 不同母带响度的歌被拉开（可能正是想要的） |
| A2 曲库自适应 | 库内 dB 的 p5/p95 | 区分度最大 | **随曲库变化 → 同一首歌在两台设备上词条可能不同** |
| A3 混合 | 固定 + 曲级归一 | 兼顾 | 复杂度高，收益不明 |

**推荐 A1。** A2 的不可复现性是硬伤（删一首歌可能让别的歌词条变化，用户会认为功能有 bug）。
"燃/静谧"本来就是**绝对能量**概念，物理标定与语义一致。

### 3.4 与 VA 头的关系

arousal **不再取自 VA 头**（头仍输出 arousal，但被 RMS 覆盖）。
valence 继续取自 VA 头——它是 YAMNet→valence 的学习结果，有信息（V 轴贡献 51.6%）。

**必须验证**：valence 单独用是否还够好？→ §3.5 已给出一个必须一并修的缺陷。

### 3.5 一个已存在的锚点设计缺陷（必须一并修）

> **"元气"(0.6, 0.4) 与 "治愈"(0.6, −0.1) 的 `anchorV` 完全相同。**

双轴投票时这两组只靠 arousal 区分。而这两个词条占了 **36% 的窗**（18.6% + 17.3%）。
一旦 arousal 换成绝对 RMS，它们的区分度完全押在 RMS 的分辨力上。

→ 这是 §5 锚点重标定必须覆盖的（两组必须拉开 `anchorV` 间距）。

## 4. 方案 B：valence 零点/斜率标定

### 4.1 三个候选

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **B1 固定标定**（推荐） | `v' = (v − B) / S`，B/S 由大规模曲库标定后写死 | 可复现、可解释、不依赖运行时状态 | 不同曲库的用户拿到同一组 B/S |
| B2 曲库自适应 | 运行时按本机曲库算 B/S | 每个用户的库都居中 | **删歌/加歌/分析进度不同 → 同一首歌词条会变** |
| B3 曲内相对 | `v − song_mean_v` | 完全消掉曲级偏置 | **语义变成"这首歌内部相对多正"**——全程都很悲的歌会趋近 0，反而判不出来。不可取 |

**推荐 B1。** B2 的不可复现性与 A2 同源，是同一个坑。

本次诊断给出的标定候选：曲库 valence 歌级 mean **+0.249**、std **0.242**
→ 候选 `B = 0.25, S = 0.85`（保留原尺度的一半 spread，避免过度放大噪声）
→ 需在离线模拟里对比几组 (B, S) 再定。

### 4.2 一个诚实的边界

valence 的正偏里，**有多少是模型偏、多少是曲库偏，无法分离**（没有真值）。
B1 假定"库均值应接近 0"——这在 ACG/OST 曲库上未必成立。

**缓解措施**：标定后**人工抽查 20 首**（听一下标定后的词条对不对），结论写进本文档。
这是唯一能在无真值条件下做的验证。

## 5. 方案 C：锚点重标定（必须跟随 A/B）

### 5.1 算法

1. 在**重标定后的逐窗输出**上做 9 簇 k-means
   （⚠️ 必须在**逐窗**上做，不是在歌级均值上——歌级均值方差被平均掉了，测的是别的东西）
2. 簇心与 9 个 `auto=true` 组锚点做 1-1 匹配（贪心最小距离，约束每个组恰好配一个簇）
3. 新锚点 = 簇心；迭代 2~3 轮（锚点变 → 分布变 → 再聚类）
4. 手动组（WITTY）不参与，无自动锚点

### 5.2 硬约束

- 锚点保持在 [-1, 1]² 内
- 组间最小间距 ≥ **0.25**（否则两个词条无法区分；这也会自动解决 §3.5 的"元气/治愈同锚点"）
- 锚点距离中心的最大值不宜超过 0.6（超出说明模型够不到，该组应当合并或调整语义）

### 5.3 风险（必须写进决策）

> **锚点重标定只让分布变好看，不让模型更准。**
> 没有真值就无法证明新的更好。它的正当性**完全来自**：A/B 改完后锚点必须跟着新分布走，否则更错。
> **不能单独做。**

**模拟补充的两条（§10）**：

1. **必须带位移约束**。本库不存在「高 V + 低 A」的组合（安静的歌都偏伤感），
   无约束匹配会把「治愈」配到**高能量**簇上——那不是不准，是**语义反了**。
   约束的做法：簇心离该组**原语义锚点**超过 `MAX_SHIFT`（定稿 0.40）就不参与匹配，
   该组**保持原锚点**。宁可让词条稀有，也不让它说反话。
2. **位移比较必须在标定前坐标系里做**。B 把 V 整体平移了约 0.29，
   若直接在标定后空间比较距离，这个平移会被误算成"语义漂移"，
   于是所有组都超限、锚点一个都不动，**C 退化成 no-op**。
   正确做法：把簇心用逆变换 `v0 = v*S + B` 还原回标定前空间再比距离。

旧数据保留在库里不被覆盖（除该曲重扫外）。

## 7. 明确不做的事

- **不重训 VA 头**——诊断显示输出健康（稳定率 81.2%、未定率 11.9%），且无真值无法验证"更准"
- **不换表征**（MERT/CLAP/Music4All）——`EMOTION_KNN_ANALYSIS.md` 已全部实测判负
- **不对齐外部 V/A 数据集**——曲库是 VOCALOID/动画 OST（552 艺人），非 Jamendo，无现成标注
- **不动词表规模**（10 组 39 词）
- **不把 ICC 0.66 当缺陷修**——它是表征性质；可作为推荐信号正向利用（见 §8）

## 8. 一个可以顺带做的正向利用

ICC 0.66 意味着"同一艺人的歌被模型给相近分数"。
在**推荐**场景这是有效信号（用户喜欢澤野弘之的燃曲 → 推同艺人的燃曲命中率高）。

具体：探索播放补队列时，把"同艺人 + 标签一致"作为加权项。

**前提是诚实改名**——UI 上别再把这个信号叫"情绪"，可以叫"同风格/同制作人"。
这样 ICC 从"测量缺陷"变成"可利用的亲和度信号"。

## 10. 离线模拟结果（2026-10-24，参数定稿依据）

工具：`tools/emotion_sim.py`（复用 `emotion_diag.py` 的投票逻辑，避免两处失真）。

```powershell
# 音频样本：从设备拉真实音频（adb exec-out cat → <songId>.<ext>）
python tools/emotion_sim.py --db melody.db --audio <音频目录>
# 全库 valence 侧分析（不需要音频，1094 首全参与）
python tools/emotion_sim.py --db melody.db --audio <目录> --full-library --only-no-a
```

**样本口径**：真实音频样本 69 首（覆盖 16+ 艺人，含 FLAC 96k/24bit、MP3、M4A、WAV），
拉取后用 ffmpeg 解码成 16k mono，按 5s 窗/2.5s hop 算 RMS→dB（窗口起点与
`EmotionAnalyzer` 的滑窗逐窗对齐）。valence 侧分析跑全库 1094 首。

### 10.1 真实响度分布

**（a）ffmpeg 路径**（初版模拟用的口径）：```
min -87.8 dBFS | p5 -28.1 | median -11.8 | p95 -5.2 | max -3.4
```

**（b）app 精确路径**（`EmotionAnalyzer` 实际走的路径，真机复核后重标）：```
p1  -43.34 | p5  -31.19 | p25 -19.58 | p50 -14.76 | p75 -11.40 | p95  -8.20 | p99  -7.32
min -89.80 | mean -16.76 | max -6.41
```

> ⚠️ **两条路径差约 3 dB，参数必须按 (b) 定。**
> 原因：`EmotionAnalyzer.resampleTo16k` 是**线性插值重采样**（无抗混叠滤波），
> 高频折叠使 RMS 略低于 ffmpeg 的带滤波重采样。
> **这不是 bug，也不能改**——同一份 PCM 还要喂给 YAMNet，改重采样会破坏
> 「与服务端训练逐位一致（maxDiff=6e-6）」的前提。正确做法是**按 app 实际口径标定映射区间**。
>
> 真机复核（2026-10-24）：取已重扫的歌，把真机曲线反解成 dB，与本地按 app 路径
> 复现的 dB **中位差 -0.00 dB** —— 真机测的就是它该测的，无系统性电平 bug。

**这个库比预想的响**（app 路径中位 -14.8 dBFS）。它直接否掉了 A1（-60..0dB）：
-60dB 的下限对 p5 只有 -31dB 的库来说太深，低能量段几乎不可达
（低能可达仅 **0.9%**），「静谧」「窒息」这类词条永远出不来。

| 方案 | 燃可达%（arousal≥+0.6） | 低能可达%（≤−0.5） | 判读 |
|---|---|---|---|
| A1 (-60..0) | 29.3 | **0.9** | ❌ 低端不可达 |
| A2 (-45..0) | **9.5** | 3.0 | ❌ 两端都不行 |
| A3 (-40..-5) | 29.3 | 4.9 | ❌ 低端仍不可达 |
| A6 (-40..0) | **3.8** | 6.0 | ❌ 高端不可达 |

### 10.3 三个关键结论

**① A（RMS）是必需的——它是唯一能救「燃」的一步**

top1 词条分布（用户实际看到的词）：

| | 治愈 | 静谧 | 神圣 | 放松 | 元气 | 躁 | emo | 窒息 | **燃** |
|---|---|---|---|---|---|---|---|---|---|
| 现状（全库 1094） | 519 | 164 | 451 | 576 | 457 | 138 | 210 | 73 | **154** |
| 只做 B（保留原锚点，全库 1094） | 282 | 227 | 182 | 111 | 99 | 67 | 60 | 44 | **22** |
| **A7+B（保留原锚点，样本 69）** | 2 | 4 | 7 | 3 | 30 | 4 | 1 | 1 | **17（24.6%）** |

valence 标定把 V 均值拉向 0 之后，「燃」这类**高能量**词条几乎归零（22 首 / 2.0%）——
因为模型的 arousal 够不到 +0.85（曲风代理的固有限制）。
换成**真实响度**后，「燃」回到 24.6%。**这是 A 不可替代的价值。**

**② B（valence 标定）是有益的——全库指标全面改善**

| 指标（全库 1094 首） | 现状 | B1 + 保留原锚点 |
|---|---|---|
| 歌级 V 均值 | +0.264 | **+0.114** |
| 词条覆盖极差 | 6.03× | **2.71×** |
| 冷门词条最少歌数 | 16 | **3** |
| 半曲一致性 | 48.5% | **62.3%** |
| Bootstrap 稳定率 | 81.1% | **85.4%** |

**③ C（锚点重标定）实测下来不必做——保留原锚点反而更好**

同批样本内横向比较（保留原锚点 = 「不C」）：

| 方案 | 词条极差 | 稳定率% | 半曲一致% |
|---|---|---|---|
| 现状 | 13.4 | 84.7 | 59.4 |
| **A7+B1+不C（保留原锚点）** | **7.17** | **90.5** | **65.2** |
| A7+B1+C（位移约束 0.25） | 9.14 | 88.4 | 59.4 |
| A7+B1+C（无位移约束） | 5.12 | 82.0 | 47.8 |

全库侧同样：不做 C 的词条极差 **2.71×** vs 做 C 的 6.33×。

**原因**：A 的映射区间选对之后（-30..-5dB），**原锚点在新坐标下依然语义正确**
（燃→-6.9dB / 治愈→-18.8dB / 静谧→-24.4dB，量级都对得上）；
而 C 的 k-means 要在 9 个簇和 9 个组之间做 1-1 分配，**高能量簇的划分噪声很大**
（69 首样本上「躁」的 arousal 在两次运行间从 +0.676 跳到 +0.375），
位移约束又让 C 大部分退化成 no-op，剩下的移动反而引入语义漂移。

**C 降级为「重扫后的可选复查项」**——锚点只影响投票、不影响存储的曲线，
所以重扫后想再算一次是零成本的（不必再扫一遍）。

<details>
<summary>若将来仍要做 C，两个必须避开的坑</summary>

1. **必须带位移约束**。本库不存在「高 V + 低 A」的组合（安静的歌都偏伤感），
   无约束匹配会把「治愈」配到 `(+0.561, +0.852)`——**高能量位置**，语义直接反了。
   约束做法：簇心离该组**原语义锚点**超过 `MAX_SHIFT`（0.40）就不参与匹配，
   该组**保持原锚点**。宁可让词条稀有，也不让它说反话。
2. **位移比较必须在标定前坐标系里做**。B 把 V 整体平移了约 0.29，
   若直接在标定后空间比距离，这个平移会被误算成"语义漂移"，
   于是所有组都超限、锚点一个都不动，**C 退化成 no-op**（实测偏移与「不C」完全相同）。
   正确做法：簇心先用逆变换 `v0 = v*S + B` 还原回标定前空间再比距离。

</details>

### 10.4 参数定稿

| 参数 | 取值 | 依据 |
|---|---|---|
| **A 映射区间** | `−30 .. −5 dBFS → [−1, 1]` | 固定物理区间（不随曲库变——自适应区间会导致同一首歌在两台设备上词条不同）。语义自洽：燃→−6.9dB / 治愈→−18.8dB / 静谧→−24.4dB。低能可达 10.0%、燃可达 36.5% |
| **B 标定** | `v' = (v − 0.25) / 0.85` | B=0.25 来自**全库**歌级 V 均值 +0.249（+0.264 是含 clamp 前的实测值）；S=0.85 保留原尺度八成、避免过度放大噪声 |
| **C 锚点** | **按全库真值重标定** | §10.3③ 的结论基于 69 首样本，在全库真值上是**错的**——详见 §11 |
| **A 的备选** | A4 自适应（库内 p5..p95） | 分布最均衡，但**不可复现**——同一首歌在两台设备上可能得到不同词条。**不采用** |

### 10.5 已拍板的产品决策

**「治愈」会变成稀有词条 —— 已接受**（2026-10-24）。
原因是语料属性而非 bug：本库的「高 V + 低 A」（愉悦但安静）组合本来就少，
现状下「治愈」有 519 首是因为 valence 正偏把大量歌推到了 +0.3~+0.6 附近——
**那不是「治愈」，是正偏的副产品**。改造后「治愈」只剩个位数曲目的占比，
其余词条重新分化——这正是这次改造的意图。

### 10.6 实现（2026-10-24 已落地）

1. **`EmotionAnalyzer`**：`resampleTo16k` 之后按 5s 窗算 RMS→dB→arousal

   VA 头的 arousal 输出不再使用（仍保留 valence 输出）。
   代价：每窗多约 8 万次乘加，实测占总耗时 <0.3%（YAMNet 推理仍是主要成本）。
2. **`EmotionGroup`**：**不动**（锚点保持原值，见 §10.3③）。
3. **`MODEL_VERSION`** → `yamnet-va-v4-rms`（触发全量重扫）。
4. **测试**：`EmotionAnalyzerArousalTest` 钉死映射区间两端（-30dB→-1、-5dB→+1）、

5. **重扫后**：用 `tools/emotion_diag.py` 复跑，按 §2 判据表验收（**这次是全库真值**）；

   **无需再次重扫**。
6. **长期**：积累 `userTagsEdited=true` 的独立纠正样本，作为「更准」的最终裁判。

### 11.3 为什么锚点必须重标定（§10.3③ 被推翻）

§10.3③ 曾基于 **69 首样本**判定"C 不必做"。全库真值推翻了它：

- 改造后「神圣」旧锚点 (+0.20,+0.50) 恰好落在新云**最密的位置**，
  退化成万能桶，逐窗占比冲到 **23.9%**（旧系统只有 14.9%），
  top1 口径更是独占 **30.6%**（335 首），成了第一大桶——而「神圣/浩瀚/震撼/史诗」
  根本不是曲库里最常见的那种情绪。
- 同时「燃」旧锚点 (+0.30,+0.85) 在新 arousal 尺度下**够不到**
  （新 arousal 最高才到 +1.0，但分布中位数已经是 +0.25），
  逐窗占比掉到 4.5%、top1 只剩 46 首——**方案 A 的成果被锚点吃掉了**。

> 根因：锚点属于**坐标系**。A 改了 arousal 的定义、B 改了 valence 的零点，
> 坐标系变了，锚点就必须跟着搬。这是**必然**，不是可选项。

### 11.4 怎么重标定的（工具链）

| 工具 | 作用 |
|---|---|
| `tools/emotion_diag.py --model <ver>` | 按 `modelVersion` 过滤曲线（改造前后必须分开统计，否则数字是混合的） |
| `tools/anchor_fit.py` | 用「改造前/后」两库配对做**经验映射**（valence 线性 R²=0.983；arousal 分位数映射），产出「语义参考点」候选 + 真指标复核 + 验收矩阵 |
| `tools/anchor_opt.py` | 在语义蓝图盒子里采样可行起点，坐标下降 + 随机重启，**硬约束**满足产品判据 |
| `tools/emotion_diag.py` 的 `PRE_VA_ANCHORS` | 冻结的**改造前**语义锚点，工具的语义序约束以此为准，不随 `EmotionGroup` 变动 |

被否掉的候选（都有硬伤）：

| 方案 | 为什么否 |
|---|---|
| 纯分位数映射（语义参考点） | 「燃」只剩 4.9% 窗占比——违背方案 A 的初衷；「神圣」仍占 20.9% |
| Lloyd 定点（向数据簇心漂移） | 把「燃」的 arousal 从 +0.755 拽到 +0.490，**稳定性反而下降**；「放松」valence 变负，语义反了 |
| 手工语义网格 | 稳定性没提升（84.3%），「神圣」仍占 20.4% |
| 只跑 k-means 1-1 匹配 | 簇↔组对应关系无约束，「治愈」会被配到高能量簇（语义反了） |

**最终做法**：11 条硬判据 + 4 项软指标，在全库真值上枚举优化。

硬判据（语义与占比）：燃=最高能量 / 静谧=最低能量 / 窒息=最负面 /
元气与治愈并列最高正面 / 负面组恰为 {emo,躁,窒息} / 燃的 arousal ≥ 0.6 /
神圣窗占比 ≤ 18% / 燃窗占比 ≥ 8% / 每组窗占比 ∈ [3%,22%] /
组间最小间距 ≥ 0.25 / |锚点| ≤ 0.95。
软指标：Bootstrap top1 稳定率、半曲一致性、词条覆盖极差、冷门词条数。

### 11.7 混合坐标系：老用户升级后的过渡窗口（2026-10-25 补修）

上面"零重扫零刷新"只对**已按当前模型重扫过的曲库**成立。
老用户库里躺着的是 v3 曲线，而重扫是后台渐进式的：

|---|---|---|
| 周期（默认） | 充电 + 电量非低，每 6 小时一轮 | ≤40 首/轮 |
| 手动「立即扫描」 | 无充电约束 | ≤300 首/轮，自动续排 |

1095 首的曲库走周期路径要 **约 7 天**（实际更久）。这个窗口里，
**v3 曲线会被新锚点投票**——坐标系错配，后果是实测出来的：

| 状态 | 元气 | 燃 | 神圣 | 治愈 | 静谧 | emo | 躁 | 放松 | 窒息 |
|---|---|---|---|---|---|---|---|---|---|
| 旧库 + 旧锚点（今天的样子） | 264 | 65 | 164 | 167 | 29 | 71 | 48 | 271 | 16 |
| 旧库 + 新锚点（**错配**） | 290 | 99 | 58 | **516** | 7 | 8 | 5 | 98 | 14 |
| 旧库 + **按版本选表**（修复后） | 264 | 65 | 164 | 167 | 29 | 71 | 48 | 271 | 16 |

错配时**47.1% 的歌会变成「治愈」**，负面词条几乎消失——比改造前还糟。

**修法：锚点表按曲线所属坐标系选择。**
`EmotionGroup.anchorsFor(modelVersion)` 返回对应坐标系的锚点表
（`yamnet-va-v4-rms` → 新表，其余 → 旧表）；`emotionTagsOf` / `modelTagsOf`
把 `emotion.modelVersion` 传下去。用户手动点的坐标（`avgOfWords`）
也用同坐标系（`anchorsForManualPoint`），否则手动点在 V-A 图上与曲线错位。

修复后老用户**零感知**：每首歌在自己被重扫之前，词条与今天完全一致；
被重扫之后，自动切到新词条体系。

> 遗留（**不是**本次引入）：重扫会继承用户手动点的坐标（`userValence`/
> `userArousal` 原样搬运），而曲线换了坐标系 → 重扫后手动点会落在旧坐标系里。
> 正确做法是**从用户词条按当前锚点重新推导**（词条才是真值，坐标是派生值）。
> 这条留到下一轮。

### 11.8 这次改动的性质

- 锚点**只影响投票，不影响已存曲线** → **零重扫成本**。
- 展示词条也是**从曲线实时投票**算出来的（`emotionTagsOf` → `EmotionGroup.headlineTagsFor`，
  库里不存计算结果）→ **零刷新成本**，改完立刻生效。
- 锚点表**按曲线自己的坐标系选**（§11.7）→ 混合坐标系期间老用户零感知。
- 唯一的例外：**用户手动校准过的歌**显示的是用户词条（`userTags` 优先），
  不受锚点影响——这是设计如此。

### 11.9 遗留问题（下一轮）

1. **重扫继承的手动点坐标会过期**（§11.7 末段）：重扫后手动点还在旧坐标系里。
   修法是从用户词条按当前锚点重新推导。
2. **「神圣」仍是中心桶**（14.3%），语义上"史诗"不该这么常见。
   下一步要么给它换个更中性的名字，要么把它的锚点往外挪——这属于词表运营，
   不是数学问题。
3. **「治愈」246 首仍然偏少**（用户已接受稀有），要持续观察
   `userTagsEdited=true` 的独立纠正样本里「治愈」的出现频率。
4. **ICC 的产品化利用**（§8）还没做：模型明显在认"谁唱的"，这是推荐信号，
   但 UI 文案必须诚实（说"同风格/同制作人"，不要说"情绪一致"）。
5. **锚点重标定的流程应该可以一键复跑**。目前是
   `anchor_opt.py` → `anchor_fit.py` → 手抄进 `EmotionGroup.kt` → 手改 4 个工具镜像，
   容易走样。理想状态是单一真源 + 生成镜像。

## 14. 人声维度：valence 的「人声偏置」与它的数据化（2026-10-25）

### 14.1 现象

真机 64 首音频离线评估（Essentia MusiCNN+DEAM 头 对照 现网 YAMNet+VA 头）发现：
现网 valence 与「有没有人声」存在系统性关联。

> ⚠️ **2026-10-25 晚更正**：下面这组数字来自 **64 首非随机样本**（为覆盖多艺人
> 多风格而挑选），**不能代表全库**。全库 1095 首真值见 §16.1，结论方向一致
> 但强度差很多（组间差 −0.164 相当，人声↔valence 的相关只有 +0.122 而非 +0.530，
> 控制 arousal 后更只剩 +0.063）。**+0.530 这个数不要再当结论引用。**

| 分组 | 首数 | 现网 valence 均值 | 未定带占比 |
|---|---|---|---|
| 器乐组 | 37 | +0.034 | 45.9% |
| 人声组 | 27 | +0.188 | 25.9% |

组间差 **−0.154**（MWU z=−2.54，p=0.0112，95%CI [−0.267, −0.040]），
人声概率与 valence 的相关系数 **+0.530**。也就是说，valence 有一部分在测
「有没有人唱」，而不是「什么情绪」。

### 14.2 但这不等于「模型错了」

必须说清的边界：上面测到的是**差异**，不是**偏差**。器乐曲是否真的更哀伤？
纯器乐确实常被写成抒情/沉郁的作品，模型有可能判对了。

要区分「偏差」与「真实差异」，需要**器乐曲的人工标注真值**。目前能找到的
唯一来源是 2025 年的中文传统器乐情绪数据集（87 个纯器乐片段、234 名参与者、
valence/arousal 等六维、CC BY 开放获取）：规模只够当验证集，不够做标定。

所以这一节只做**把变量显式化**，不做「校正」。校正的成立与否，等 14.3 的数据
到位后用该数据集判定。

### 14.3 改动：把「有没有人声」变成显式数据

关键发现：**App 里那个 `emotion_yamnet.tflite` 本来就在输出 521 个 AudioSet
类别分数**（输出张量 `Identity_1[2,521]`），只是分析器一直只取 embedding
（`Identity[2,1024]`），把类别分数扔掉了 —— 也就是说「这歌有没有人声」
这个信息是**白拿的**：同一个 Interpreter 多读一个输出张量即可，
**不换模型、不加 APK 体积、不涉任何新授权**。

改动清单：

| 位置 | 改动 |
|---|---|
| `player/YamnetClassMap.kt`（新增） | AudioSet 人声类 11 个索引 + 器乐类 50 个索引。索引来自官方 `yamnet_class_map.csv`（521 个具名类，索引即模型输出序号），由评估脚本从 CSV 生成后转写，勿手改 |
| `player/EmotionAnalyzer.kt` | 内层推理循环里把 `scoreArr` 的人声类分数和累加，整曲平均 → `vocalScore` |
| `core/model/SongEmotion.kt` | 新增 `vocalScore: Float?`（可空：老行为 null） |
| `data/.../SongEmotionEntity.kt` | 新增列 `vocalScore REAL` + 轻量投影同步（Room v13 → v14，`MIGRATION_13_14` 加列） |
| `app/.../EmotionScanWorker.kt` | 待扫条件加一条「已分析但 `vocalScore` 为 null」→ 老数据自动补扫一次；补完该条件自然不再命中，不会反复重扫 |

分析器里 `vocalFrames >= 1` 由既有的 `TOO_SHORT` 检查保证，所以 `vocalScore`
不会为空 —— 空值会让那一行永远被判「待补扫」，形成无限重扫。

### 14.4 为什么先存变量、后做校正

若直接改标定常数，每改一次就要全库重扫（实测约 2 小时）。先把变量存下来，
之后无论标定怎么定，都能**离线重算、零重扫**。这与 §13 提到的「存原始输出」
是同一个思路。

### 14.5 尚未落地（依赖 14.3 的数据）

- **条件标定** → **已落地，见 §16**（2026-10-25）。按人声/器乐分组给 valence
  做补偿（读时派生，零重扫）。「差异 vs 偏差」的裁决不用人工真值 ——
  用 **arousal 匹配 + 独立模型互证**（§16.3）：独立模型匹配后残余差 ≈0，
  现网几乎不缩。
- **置信度暴露** → **已落地，见 §15**（2026-10-25）。把 top 组占比当作置信度，
  区分「这歌真的平淡」与「模型自己说不准」（评审 P3 一直缺的那个信号）。
  这一项**不依赖**人声维度，可独立做，且它需要的量在 `categoriesFor` 里本来
  就算出来了，只是被扔掉。
  —— §15 的结论修正了这句的对立面：「真平淡」在当前坐标系下**测不到**
  （冷暖两轴都贴 0 的歌一首都没有），真正与「模型说不准」相对的是
  「词条自相矛盾」，不是「歌本身平淡」。

### 14.6 同期结论：换基座不划算

同一轮评估顺带验证了「换 Essentia 的 DEAM 头」这条最省事的换法（详见
`.emotion-diag/essentia-eval/essentia-eval-findings.md`）：

| | 未定带 | \|v\|>0.5 占比 | 与现网 valence 相关 |
|---|---|---|---|
| 现网（YAMNet+VA 头） | 37.5% | 6.2% | — |
| DEAM 头（全局重标定后） | 45.3% | 4.7% | +0.348 |

DEAM 头在**有人声**的歌上 81.5% 打不出分（器乐组只有 40.5%），方向与预期相反；
换过去等于换一个判别力更弱、授权更受限（Essentia 模型默认 CC BY-NC-ND，商用
需单独申请）、还需重做端云一致性的模型，而收益为零甚至负。**故不换基座。**


## 12. 词条并列的确定性排序（2026-10-25）

### 12.1 现象与根因

票数是整数，所以**比例并列**很常见。在真机全库 1095 首上实测：

| 现象 | 首数 | 占比 |
|---|---|---|
| top1 比例并列（并列会决定**标题词**） | 17 | 1.6% |
| 展示集合内存在比例并列（并列会决定**词条先后**） | 92 | 8.4% |

而 `categoriesFor` 原本只按占比降序排：

```kotlin
.sortedByDescending { it.second }
```

`sortedByDescending` 是**稳定排序** —— 并列项保持输入顺序，而输入顺序来自
`votes` 这个 `HashMap` 的迭代序。Kotlin 枚举没有覆写 `hashCode()`，走的是
`Object.hashCode()`（identity hash），**契约上不保证跨进程一致**。

结论：**同一首歌的词条先后，可能随 App 重启而变**；而且 App 的排列约定
与离线镜像（Python/numpy）不同，导致"设备 vs 镜像"回归比对无法逐字对齐
—— 装机复核时 18 首抽样里有 1 首（`A Sky Full of Stars`，元气 27 票 /
神圣 27 票）集合一致但顺序不同。

### 12.2 修法：并列时按组声明序兜底

```kotlin
.sortedWith(
    compareByDescending<Pair<EmotionGroup, Float>> { it.second }
        .thenBy { it.first.ordinal },
)
```

**先按占比降序（主序不变），并列时按 `EmotionGroup.ordinal`（组声明序）升序**。

选组声明序而不是别的兜底，有三个理由：

1. **确定性**：与锚点表无关，重标定锚点、切换坐标系都不影响并列时的先后。
2. **跨坐标系稳定**：与 §11.7「锚点必须按坐标系分表」的原则一致 ——
   同一个用户的两套坐标系下，同一对组的并列先后不会变。
3. **好解释**：组声明序（元气→燃→神圣→鬼畜→治愈→静谧→emo→躁→放松→窒息）
   本身就是一张展示顺序表，不需要额外维护一份优先级表。

### 12.3 影响面（全库 1095 首实测）

| 指标 | 数值 |
|---|---|
| top1 会变的歌 | 4 首 |
| 展示顺序会变的歌（集合不变） | 17 首 |
| top1 分布变化 | 静谧 +3、神圣 +1、放松 −2、emo −1、治愈 −1；元气/燃/躁/窒息 不变 |

即：改动只影响并列的那部分歌，**词条集合一个都没变**，只有先后与个别
top1 标题词按确定性规则落位。

### 12.4 镜像与测试同步

- `tools/emotion_diag.py`：新增 `sorted_group_order(ratios, group_index=None)`，
  用 `np.lexsort` 实现「占比降序 + 组声明序升序」；`groups_to_tags` 与
  bootstrap 稳定性统计都改用它。
- `tools/emotion_sim.py`：`tags_of` 与锚点拟合的 bootstrap 同步改用该 helper。
  （`tags_of` 的下标是 auto 数组下标，需要传 `order` 映射回 GROUPS 下标，
  否则兜底序会变成 auto 序而不是组声明序。）
- 新增 `core/model/src/test/.../EmotionGroupVoteOrderTest.kt`（4 例）：
  并列按声明序、重复调用结果可复现、并列先后不随锚点表变、占比仍然优先于声明序。

### 12.5 真机复验

Redmi 23113RKC6C（Android 16）装新包后逐首比对：

## 13. 版本单一真源 + 手动点坐标派生（2026-10-25）

§11 把锚点表按坐标系分开了，但**坐标系本身怎么被标识**还是手写的 —— 这一节把
那部分也收口，顺带修掉"手动点坐标过期"。

### 13.1 问题：版本标识是手写字符串

改造前：

```kotlin
// core/model/EmotionGroup.kt
const val CURRENT_MODEL_VERSION = "yamnet-va-v4-rms"
// player/EmotionAnalyzer.kt
const val MODEL_VERSION = EmotionGroup.CURRENT_MODEL_VERSION
// app/EmotionScanWorker.kt
pending = songs.filter { analyzed[it.id] != EmotionAnalyzer.MODEL_VERSION && ... }
```

**整个重扫触发就挂在这一个手写字符串上。** 换了 `emotion_va_head.tflite`、
或改了 A/B 常量，却忘了改这个串 → `pending` 永远为空 → 日志还打
`library up-to-date (1098 songs)` → **老数据静默留存、永远不重扫**。

这不是假想：A/B 改造就是改了坐标系，那个串是我手动从 `yamnet-va-v3` 改成
`yamnet-va-v4-rms` 的。**下次就可能忘。**

### 13.2 修法：版本串 = `<坐标系标签>@<内容指纹>`

单一真源落在 `core/model/emotion_model_spec.properties`（新增）：

```properties
label = yamnet-va-v4-rms
dbFloor = -30.0
dbCeil = -5.0
vCalBias = 0.25
vCalScale = 0.85
yamnetSha256 = db0bb6fb...
headSha256 = edbc3e4e...
```

`:core:model` 的 `generateEmotionModelSpec` 任务（新增）做两件事：

1. **校验两个 tflite 的 SHA-256 与清单一致** —— 不一致就**构建直接失败**，
   附一句"换了资产必须更新清单 / 评估坐标系 / 重扫"。
   → 「换了资产忘了改版本号」从此**不可能静默发生**。
2. 算出指纹并生成 `EmotionModelSpec.kt`（生成物，勿手改）：

   | 常量 | 含义 | 用途 |
   |---|---|---|
   | `LABEL` | 坐标系语义身份（人可读） | 锚点表按它选 |
   | `PARAMS_FINGERPRINT` | 坐标定义（label + A/B 参数）哈希 | **守锚点表** |
   | `FINGERPRINT` | 坐标定义 + 资产哈希 | 写进 `modelVersion` |
   | `MODEL_VERSION` | `<label>@<fingerprint>` | 写进 `song_emotions.modelVersion` |
   | `DB_FLOOR/DB_CEIL/V_CAL_*` | A/B 参数 | `EmotionAnalyzer` 引用（不再各写一份） |

**为什么标签与指纹要分开**：标签是**坐标系**的身份，指纹是**这一版模型**的身份。
换模型资产（重训 VA 头）→ 指纹变 → 重扫，但坐标系没变 → 标签不变 → 锚点表不变。
换坐标系语义（改 A/B 参数）→ 标签必须变 → 锚点表也要重标定。
两件事独立，才不会互相绑死。

### 13.3 锚点表按标签选 + 参数指纹守锚点表

```kotlin
fun anchorsFor(modelVersion: String) = when (modelVersion.substringBefore('@')) {
    CURRENT_MODEL_LABEL -> CURRENT_ANCHORS
    LEGACY_MODEL_LABEL  -> LEGACY_ANCHORS
    else                -> LEGACY_ANCHORS
}
```

而"改了 A/B 参数却没重标定锚点表"这个错，由**参数指纹**守住：

```kotlin
// 刻意硬编码, 不引用生成物 —— 只有硬编码才能当"标定时点的凭据"
const val ANCHORS_CALIBRATED_FOR = "09ee136b"
```

`EmotionModelSpecTest` 拿它跟当前 `PARAMS_FINGERPRINT` 比 —— 改了参数而没重标定
锚点表，**单测会红**。这把"改了坐标系却沿用旧锚点"（实测 47.1% 的歌变「治愈」）
从静默错误变成响亮的构建失败。

### 13.4 手动点坐标：从"存"改成"读时派生"

**词条是真值，坐标是派生值。** 原来是：标记时按当时的锚点算好坐标写进
`userValence/userArousal`，重扫时**原样继承** —— 曲线换了坐标系，坐标还停在旧的。

真机实测（改造前的库，3 首用户校准的歌）：

```
「僕は...」/ Blue[3-6]   存的 v=+0.250 a=+0.675
                        当前坐标系应该是 v=+0.119 a=+0.442
```

现在：

```kotlin
// SongEmotion.kt —— 读时派生，不读库里那两列
private fun userPoint() = if (userTags.isEmpty()) null
    else EmotionGroup.avgOfWords(userTags, EmotionGroup.anchorsForManualPoint(this))
val effectiveValence get() = userPoint()?.first ?: valence
```

连带改动：

| 位置 | 改什么 |
|---|---|
| `SongEmotionsRepository.upsert` | 只继承**词条** + `userTagsEdited`，不继承坐标 |
| `SongEmotionsRepository.saveCorrection` | 只写词条，坐标列置 NULL |
| `MelodyDao.emotionCorrectionCount` | `userValence IS NOT NULL` → `userTags IS NOT NULL`（否则校准数直接归零） |
| `AppMediaMetadataViewModel` | 不再算 avg 往下传；改用 `groupOf` 校验词表合法性 |

> 顺带修了一个小坑：`avgOfWords` 会**静默丢弃**非法词（只剩一个合法词时照样
> 返回坐标），不能拿它当词表校验器 —— 校验改成 `words.any { groupOf(it) == null }`。

### 13.5 数据迁移 v12 → v13

```sql
-- ① 当前坐标系的行补上内容指纹 -> 零重扫
UPDATE song_emotions SET modelVersion = '<label>@<fp>' WHERE modelVersion = '<label>'
-- ② 坐标列清空(改成读时派生), 词条保留 —— 词条才是真值
UPDATE song_emotions SET userValence = NULL, userArousal = NULL
  WHERE userTags IS NOT NULL AND userTags <> ''
```

老坐标系（`yamnet-va-v3`）的行**不补指纹** → 仍待扫（标签不同 → 用旧锚点表），
这是对的：它们本来就该重扫。

> 以后换了资产，**不需要新迁移** —— 指纹进了版本串，老行与新串不等，
> `EmotionScanWorker` 的待扫判定自动把它们排进队列。

### 13.6 Python 镜像不再手抄

`tools/emotion_diag.py` 以前**手抄**了一份 Kotlin 的锚点表（`GROUPS` /
`LEGACY_GROUPS` / `CUR_MODEL_VERSION`）。漂移是真实发生过的故障：§12 那轮我
把 auto 数组下标与组声明序搞混，靠单测与镜像互校才发现。

现在 `tools/emotion_mirror.py`（新增）**直接解析源文件**：

- `core/model/.../EmotionGroup.kt` → 枚举常量（词 + 新锚点 + auto）+ `LEGACY_ANCHORS`
- `core/model/emotion_model_spec.properties` → 标签 + 参数 + 资产哈希 → 算指纹

指纹算法必须与 Gradle 侧**逐字一致**，所以镜像会跟 `:core:model` 的生成物
**交叉校验**，对不上直接抛错。

工具按 `modelVersion` 过滤的地方也改成**标签前缀匹配**
（`modelVersion LIKE 'yamnet-va-v4-rms%'`）—— 按精确串过滤的话，每次换指纹
都得改工具。

## 15. 置信度：把「模型有没有把握」露出来（2026-10-25）

### 15.1 先把问题问准：P3 的「未定 vs 平静」不是那个「未定」

原以为 P3 说的是 UI 上那个 `tags.isEmpty() -> "未定"` 分支。**实测否掉了**：

| 状态 | 首数 | 占比 |
|---|---|---|
| 词条为空（走「未定」分支） | **0** | 0.0% |
| 词条非空 | 1092 | 99.7% |
| （另有用户手动标记） | 3 | — |

只要有一组票过 15% 就有词条，而投票几乎不会全部摊平到 15% 以下 ——
那个分支**在真实库里从来不触发**。所以「未定 vs 平静」分不清的，不是它。

真正在发生的事是另一回事：

> **29.0% 的歌（318 / 1092）词条里同时冒出暖词和冷词** ——
> 「治愈 · emo」「燃 · 窒息」「静谧 · 躁」。

票摊得开，词条就会自相矛盾。用户看到无从判断：**这歌真这么矛盾？还是模型自己没把握？**

### 15.2 关键发现：「真平淡」在当前坐标系下不是一类

原计划用「valence 未定」当「平淡」那一侧。**数据不支持**：

- **valence 未定 431 首，但没有一首是「冷暖两轴都贴 0」的** ——
  有效窗 `mean|v|` 的 p10 就有 0.260，`mean|a|` 的 p10 是 0.247。
  所谓「两轴都平淡」的歌一首都没有。
- **valence 未定 ≠ 平淡**：这 431 首里 76% 的 top1 组是
  「燃 / 神圣 / 静谧 / 放松」，而这些组的 `anchorV` 本身就在 0 附近
  （燃 0.009、神圣 0.228、静谧 0.078、放松 0.012）。
  valence 未定主要意味着「冷暖方向互相抵消」或「落进了 anchorV≈0 的组」。

结论：**跟「模型说不准」对立的那个面（真平淡）在当前坐标系下测不到。**
所以提示只讲把握，不讲平淡 —— 讲「这首歌平淡」是没有数据支撑的断言。

### 15.3 改动

| 位置 | 改什么 |
|---|---|
| `EmotionGroup.voteRatios`（新） | 抽出投票底座：完整比例表，**不过滤、不截断** |
| `EmotionGroup.confidenceOf`（新） | top1 占比 = 把握程度 |
| `EmotionGroup.categoriesFor` | 改为 `voteRatios` 的过滤视图（**行为不变**） |
| `core/model/EmotionConfidence.kt`（新） | `emotionConfidenceOf` / `needsConfidenceHint` / `LOW_CONFIDENCE_RATIO` |
| `core/ui/SongEmotionSection.kt` | 低把握时在词条下加一行小字 |

UI 文案：**「模型把握不大，词条仅供参考」**。

判定：`top1 < 0.35` 且 **用户未手动标记**（手动标记时展示的是用户自己的词，
模型的把握程度与用户看到的词无关，提示只是噪音）。

坐标系统一：`emotionConfidenceOf` 走 `anchorsFor(modelVersion)`，与词条投票
用同一套锚点 —— 曲线和锚点必须同坐标系（§11.7）。

### 15.3b 置信度必须与投票用同一份曲线（2026-10-25 晚补）

§16 引入人声成分补偿后，**词条是按补偿后的曲线投票的**，所以置信度也必须
基于补偿后的曲线 —— 否则它描述的是一次**已经不存在的**投票。

`emotionConfidenceOf` 因此改用 `SongEmotion.compensatedCurve`，
并有单测锁住（补偿前后置信度不同：0.75 → 1.00）。

另外：§15.1~15.2 的观测都是在 **v4 坐标系**（全局标定、无人声补偿）上做的；
v5 上「valence 未定 ≠ 平淡」这个结论依然成立（补偿只平移器乐组，
不改「valence 未定」的比例结构），但具体数值请以 §16.6 为准。

### 15.4 信号有效性的证据

「词条是否自相矛盾」是这条提示的**外部效标**（矛盾 = 模型自己跟自己打架）：

| 组 | 首数 | top1 占比均值 |
|---|---|---|
| 词条含冷暖矛盾 | 318 | **0.392** |
| 词条不矛盾 | 774 | **0.487** |

Mann-Whitney U **p = 8.8e-22** —— 差异极显著，说明 top1 占比确实测到了
「模型有没有把握」，不是噪声。

阈值 0.35 的来源：全库分位 p25 = 0.345。以 0.35 切 ——
低把握那批 **44.7%** 词条自相矛盾，高把握那批只有 **23.6%**，
分界线正好落在「矛盾开始扎堆」的位置。

### 15.5 未落地 / 边界

### 15.6 单一阈值不够：加「词条自相矛盾」这一个维度（2026-10-25 晚补）

真机复核时用户指出一首 **RADWIMPS《陽菜と、走る帆高》**：词条是「emo · 躁」，
冷暖同现，明显自相矛盾 —— 但**没有**显示提示。查下去发现：

| | 首数 | top1 占比均值 |
|---|---|---|
| 词条含冷暖矛盾 | 228 | 0.398 |
| 词条不矛盾 | 867 | 0.484 |

Mann-Whitney U **p = 1.7e-14** —— 矛盾组整体上确实更散，但**散得不够低**：
**137 首（12.5%）的 top1 ≥ 0.45**（最高 0.80），单靠阈值抓不到它们。

> `宇治川花火大会` top1=0.800 [治愈·emo]、`新世界` top1=0.645 [燃·躁]、
> `玫瑰少年` top1=0.620 [神圣·窒息] —— 这些歌的分类其实**很确定**，
> 确定地给出了一个两极的结论。

所以把握程度改成**两档**（`EmotionConfidenceLevel`）：

| 档位 | 判据 | 含义 | 文案 |
|---|---|---|---|
| `SPREAD` | top1 < 0.35 | 票摊开 | 「模型把握不大，词条仅供参考」 |
| `MIXED` | 票集中但冷暖词同现 | 结论很确定，但两极 | 「词条里有冷有热，这首歌可能不止一种情绪」 |
| `HIGH` | 其余 | 可以放心看 | 不显示 |

两种情况对用户的含义不同，**文案也不能一样** —— 混成一句就等于没区分。

加上 `MIXED` 后，全库提示覆盖从 267 首（24.4%）升到 **404 首（36.9%）**。

### 15.6b 情绪曲库列表行也标出来了

原先只有详情弹窗有提示，曲库「情绪」Tab 的列表行（每首歌名下面那行小字）
只显示词条 —— 而**列表才是扫歌的地方**。

现在列表行的把握不足时：词条用次要色（不再是主题色）+ 末尾追加「· 不确定」。
（`EmotionSongUiRow` 加了 `confidence` 字段；`EmotionViewModel.buildRows`
算出档位带下来。）

- **情绪曲库列表行没加提示**：`EmotionSongUiRow` 只带 `tags`/`corrected`，
  不带 `SongEmotion`，算不出置信度；且列表行的 subline 只有一行，
  再塞一句文字会挤。曲库那侧要另想交互（弱化显示？只显示 top1 词？）。
- **阈值不随坐标系自动重标**：它依赖投票分布，换坐标系（改 A/B 参数、
  重标锚点表）后要重新标一次。规则已写进 `EmotionConfidence.kt` 的注释。
- **换模型资产不影响阈值**：阈值只看票型，不看绝对坐标。
- **置信度不是校准过的概率**：0.392 是「最高票占比」，不是「判对率」。
  真正的概率需要人工真值标注，那是另一件事（§14.2 同一类问题）。

## 16. 条件标定：把 valence 里的「人声成分」剥掉（2026-10-25）

§14 存了人声分数，§15 暴露了置信度。这一节是那件事的**兑现**：
valence 有一部分在测「有没有人唱」，不是「什么情绪」——这一节把它剥掉。

### 16.1 全库真值（更正 §14.1 的 64 首数字）

§14.1 的 −0.154 / +0.530 来自 **64 首非随机样本**，不能代表全库。
补扫完成（全库 1095 首 `vocalScore` 全部落库，NULL = 0）后的真值：

| 量 | 值 |
|---|---|
| Pearson(vocalScore, valence) | **+0.122** |
| Spearman | +0.215 |
| Pearson(log vocalScore, valence) | +0.237 |
| **偏相关（控制 arousal）** | **+0.063** |
| Pearson(vocalScore, arousal) | +0.178 |
| corr(valence, arousal) | +0.359 |

人声分数本身是**可靠检测器**（64 首离线样本，器乐对照 n=25）：

- 与独立测法（MusicNN vocal 概率）Spearman **+0.535~0.550**
- 器乐对照集的分离度 **AUC = 0.024**（越小越好 ⇒ 完美分离）
- 艺人聚合干净：唱作人（eill 0.058 / 茅原実里 0.037 / Taylor Swift 0.030）
  vs 纯器乐演奏家（Carlos Estella 0.0017 / Evan Call 0.0026），
  **组间 std 0.0125 >> 组内 std 0.0040**

### 16.2 分组差异：全库确认

阈值取 **valence~vocalScore 的断点 0.010**（valence 均值在此处是台阶不是斜坡：
−0.024 → +0.115），不是拍脑袋：

| 组 | 首数 | valence 均值 | arousal 均值 |
|---|---|---|---|
| 人声组（vocalScore > 0.010） | 376 | **+0.120** | +0.294 |
| 器乐组（vocalScore ≤ 0.010） | 719 | **−0.041** | −0.038 |

组间差 **−0.162**（MWU p=6.5e-20），与 §14.1 用 64 首估的 −0.154 量级一致。
阈值在 0.005~0.020 滑动时匹配后的残余差稳定在 −0.05~−0.09，不依赖阈值选择。

### 16.3 「差异 vs 偏差」的裁决 —— 不用人工真值

§14.2 说要人工真值才能区分「器乐曲真的更哀伤」与「模型在测有没有人唱」。
**用两个独立模型互证就能裁决**，不需要人工标注：

1. **arousal 匹配**：arousal 现在是物理 RMS（真实响度），人声多的歌也更多响
   （组间 arousal 差 +0.332）。在 arousal 分箱内比较，组间 valence 差从
   **−0.162 缩到 −0.091** —— 一半以上是能量效应，那部分是真信号，不该扣。
2. **独立模型对照**：同样做 arousal 匹配，
   - MusicNN + DEAM 头：原始组间差 −0.051 → **匹配后 +0.026（≈0）**
   - 现网 YAMNet + VA 头：原始组间差 −0.164 → **匹配后 −0.164（几乎不缩）**

   独立模型没有这层成分，现网有 —— **这不是「人声歌真的更正向」的音乐规律，
   是现网 valence 特有的成分**。

### 16.4 补偿量：0.091

只扣掉能量效应解释不了的那部分（−0.091），保留「器乐曲确实更安静/更沉郁」
的真实差异。校正后组间差 **−0.071**，与独立参照（−0.051）基本对齐。

### 16.8 边界与未落地

- **补偿量是「只扣能量效应解释不了的部分」的估计**，不是精确的真值：
  独立参照只有 64 首，且 MusicNN 的 vocalsProb 检出同样偏弱
  （64 首里没有一首 vocalsProb > 0.5）。改了 `vocalCompShift` 只需改规格清单，
  **零重扫**，可以随时调。
- **检出不是"普遍漏"，是"特定风格弱"**（2026-10-25 更正）：
  这里原先拿 RADWIMPS《Sea In The Sky》当"漏检"例子（说它"明明有人唱"）是**错的** ——
  那首歌**没有人声**，`vocalScore` 0.0008 是**正确检出**。

  事实是：64 首样本上器乐对照集的分离度 AUC = 0.024（近乎完美分离），
  所以 vocalScore 作为「有没有人唱」的检测器**不漏**。真正的短板是**语种/风格**：
  RADWIMPS 这类**日语主唱**的检出明显弱于英语强主唱 ——
  RADWIMPS 的 106 首 vocalScore 中位 0.0034（最高是合唱版《正解》0.1188），
  而英语强主唱高一档（Queen 0.1107 / AJR 0.0608 / SpongeBob 0.1534）。

  这些日语歌会被划进器乐组并被补偿 —— 但它们**同样**被 valence 偏置抬高，
  补偿对它们是**自洽的**（valence 里的「人声成分」量与 vocalScore 大致成正比）。
  真要更准，得把 vocalScore 口径从「帧级均值」换成「帧级高分位数」——
  实测帧级 max 能到 0.85~1.19 而纯器乐上限只有 0.03，区分度很大，
  但那需要全库重扫（~3.5 小时），且换口径后阈值要重新定。**暂不动**。
- **情绪曲库列表行的置信度提示**已补（§15.6b）：把握不足的词条改用次要色 +
  末尾追加「· 不确定」。
- 补偿只动 valence，不动 arousal —— arousal 是物理响度，本来就没有「人声成分」。

### 16.9 真机验证抓到的漏项：轻量投影少查一列

补偿落地后第一次真机验证，**曲库情绪 Tab 的词条没变**（`Dear Gilbert` 仍是
「静谧·放松·emo」，而离线复算说补偿后应是「静谧·放松」）。

排查下来不是算法问题，是**读路径少查了一列**：

- 歌曲详情弹窗走 `SongEmotionRepository.get(songId)` → **整行读** → 带 `vocalScore` ✓
- 曲库情绪 Tab 走 `getAll()` → **轻量投影**（`SongEmotionLite`）→ 投影 SQL
  与该 data class **当时都没带 `vocalScore` 列** → Room 映射成 null → 不补偿 ✗

**两条路径给出不同词条**，而真机 UI 看到的恰好是列表行那一侧 ——
差点误判成"补偿算法没生效"。

修法：`MelodyDao.allSongEmotions` / `observeAllSongEmotions` 的投影 SQL 补上
`vocalScore`，并加回归测试 `bulk read keeps the vocal score`（Robolectric 真实
Room 内存库，验证投影 SQL 本身）。

**教训**：投影漏列是**静默**的 —— 不编译失败、不崩，只是那一个字段变 null。
上一轮加 `vocalScore` 时改了实体、data class、`toLite()`、`toDomainLite()`，
却漏了 DAO 的两处 SELECT 列表。**凡是新增"读路径要用"的字段，
必须同时检查：实体列 → 投影 data class → 投影 SQL → 两处映射。**

## 17. 词条占比：把「多少」也露出来（2026-10-25）

用户问：「一首歌的情绪标签有燃、元气，现在能不能获取到它们各自在整首歌曲中的占比？」

**占比一直都在算，只是被扔掉了。**

`EmotionGroup.voteRatios` / `categoriesFor` 返回的本来就是 `Pair<组, 占比>`；
`headlineTagsFor` 一句 `.map { it.first.headline }` 把占比丢了，
于是 API（`emotionTagsOf`）和 UI 都只拿到词名。**底下有，接口没露。**

### 17.1 语义

占比 = 落在该组锚点附近的窗口 ÷ 全曲**有效窗口**（近零窗弃权）。

所以「燃 35%、元气 22%」的意思是：**整首歌 35% 的时间落在「燃」附近、
22% 落在「元气」附近**。这跟「这歌是燃、元气」不是一回事 ——
「燃 62%、元气 20%」和「元气 55%、燃 20%」听感完全不同，光看词条名字分不出来。

### 17.2 改动

| 位置 | 改动 |
|---|---|
| `core/model/EmotionGroup.kt` | 占比门槛提成常量 `MIN_RATIO`（原是 `categoriesFor` 的默认参数 0.15f） |
| `core/model/EmotionTags.kt` | 新增 `EmotionTagRatio`（词 + 占比）与 `emotionTagRatiosOf(emotion, minRatio, topN)` |
| `core/ui/SongEmotionSection.kt` | 详情页词条 chip 带占比：`[燃 62%]` |

**用户手动标记的词没有占比**（`ratio = null`）：用户选的是「我觉得这歌是它」，
没有「占比」这回事 —— 编一个 1.0 或均分出来都是在编数据。

`minRatio = 0f` 可以拿到**完整分布**（所有组，含低于展示门槛的），
给需要完整分布的算法用（比如时段播放按占比加权）。

### 17.3 占比必须跟着补偿走

占比来自投票，投票用的是**补偿后**的曲线（§16），
所以占比也必须是补偿后的结果 —— 否则展示的占比不是投票的占比。
`EmotionTagRatioTest` 有一条测试专门锁这个。

### 17.4 还没做的

- **情绪曲库列表行没带占比**：一行 subline 塞不下「燃 62% · 元气 20% · 神圣 12%」，
  会挤掉词条本身。列表保持只显示词名 + 「不确定」标记。
- **时段播放仍是二元匹配**（「有 emo 就算命中」），没改成按占比加权。
  占比数据现在能拿到了，但改匹配规则是产品决策，不是这次的范围。

## 18. 时段播放：匹配从「有没有这个词」改成「这个词占多少」（2026-10-25）

### 18.1 原先有多松

时段匹配是**纯 OR 判定**（`songs.filter { tags.any { it in mood.tags } }`）：

- 一首歌 16% 的时间落在「静谧」附近，和 70% 落在「静谧」附近，**一视同仁**
- 模型自己都没把握的词条照样算数（票摊开的歌，每个词占比都低，但只要 ≥15% 就能命中）

实测全库 1095 首（v5 坐标系）：

| 时段配置 | 现状池 | 其中 HIGH 把握 | MIXED（词条自相矛盾） | SPREAD（票摊开） |
|---|---|---|---|---|
| 深夜静谧（静谧+放松） | 458 | 54% | 65 | 146 |
| 通勤提神（元气+燃） | 636 | 70% | 30 | 158 |
| **emo 时刻（emo）** | **182** | **30%** | **67** | **60** |
| 治愈一下（治愈） | 269 | 61% | 12 | 92 |

「emo 时刻」最刺眼：**池里 182 首，只有 30% 是模型有把握的** —— 三分之二
是模型自相矛盾或自己都没把握的歌，照样被播出来。

### 18.2 改法：命中要卡占比门槛

`MoodSlotPolicy.MATCH_MIN_RATIO = 0.35`（全库分位 p25 = 0.345，与置信度阈值同值）：

> 词条在整曲里占的比例 ≥ 35% 才算命中。

效果：

| 时段配置 | 现状池 | 门槛 0.35 后 | HIGH 占比 |
|---|---|---|---|
| 深夜静谧 | 458 | 211 | 54% → **76%** |
| 通勤提神 | 636 | 417 | 70% → **95%** |
| emo 时刻 | 182 | 40 | 30% → **70%** |
| 治愈一下 | 269 | 49 | 61% → **90%** |
| 神圣时刻 | 457 | 133 | 47% → **72%** |

池子小 2~4 倍，但**每个都更实**。池子最小的「emo 时刻」仍有 40 首，
高于 `POOL_WARN_THRESHOLD`（10），不会退化成「歌曲较少，将循环播放」。

**顺带解决了一个隐患**：票摊开的歌，每个词的占比都低，加起来也过不了门槛 ——
**置信度问题被占比门槛自动吸收，不需要额外规则**。

### 18.3 用 max 不用 sum

匹配分用「任一目标词的占比」（max），不用「选中词占比之和」（sum）——
实测两者几乎等价（"只靠一个词撑着"的情况 0 首），max 更简单、更好解释。

### 18.4 改动

| 位置 | 改动 |
|---|---|
| `domain/playback/MoodSlotResolver.kt` | 新增 `MoodSlotPolicy.MATCH_MIN_RATIO = 0.35f` |
| `core/model/EmotionTags.kt` | 新增 `emotionMatchRatiosOf(emotion)`：给**完整分布**（不受展示门槛 15% 与 topN=4 限制）+ 用户标记的词按 1.0 处理 |
| `feature/player/PlayerRandomQueueFacade.kt` | `filterByMoodTags` 改成按占比卡门槛；新增注入 `moodEmotionTagRatiosOf`，**默认实现从 `moodEmotionTagsOf` 派生（每词 1.0）= 行为与改造前完全一致** |
| `feature/player/PlayerRuntime.kt` | 情绪缓存从 `Map<Int, List<String>>` 改成 `Map<Int, Map<String, Float>>`（词 → 占比） |
| `app/mood/MoodTimeSlotViewModel.kt` | 新增 `matchCount(tags)`：按与播放时一致的判定算池子大小 |
| `feature/user/MoodTimeSlotRoute.kt` | `MoodTimeSlotRouteState` 加 `poolCountOf` |
| `feature/user/MoodTimeSlotScreen.kt` | 时段卡片的池子数改用 `poolCountOf`（原来「每词计数求和」会**重复计数**同一首歌） |
| `feature/user/MoodSlotEditDialog.kt` | 编辑弹窗的池子数改用 `poolCountOf` + 说明「只算 ≥35% 的歌曲」 |

### 18.5 为什么界面数字也必须改

原来「该组合下可随心的歌曲」= **每词计数求和**。这有两个错：

1. **重复计数**：一首歌同时带「静谧」和「放松」会被算两次；
2. **门槛后不再是池子大小**：「带这个词」≠「会匹配上」。

加上门槛后这两个数会差 2~4 倍 —— 界面显示 458 而实际播 211，是**误导**。
所以两处显示都改成与播放时**同一套判定**（同一个 `MATCH_MIN_RATIO`）。

### 18.6 边界

- **用户手动标记的词按 1.0 处理**（强匹配）：那是用户自己的判断，比模型的更可信，
  不该因为模型占比低而被排除。
- **池子空 → 回退全库随机**（现状不变）；池子 < 10 → 提示「歌曲较少，将循环播放」（现状不变）。
- **排序仍是纯随机**：`RandomQueuePlanner.planRandomQueue` 默认模式是 `shuffle`，
  池内按强度排序会破坏「随机播放」的语义，所以只改了**池子**，没改**顺序**。
- **探索播放没动**：它的词条反馈是另一套机制（「喜欢/不喜欢某个词」），
  与时段匹配不是一回事，没有顺手带过去。

## 19. 探索播放：计票按词条占比加权（2026-10-25）

### 19.1 原先的问题

计票是**一刀切 1 票**：`recordSongOutcome(words, liked)` 给这首歌的**每个**情绪词条
各 ±1 票。于是：

- 一首 **80% emo / 20% 静谧** 的歌被跳过 → emo −1、静谧 −1
- 一首 **20% emo / 80% 静谧** 的歌被跳过 → emo −1、静谧 −1

**主次完全不分**。而且「只是顺带蹭到」的词（占比 15%）和「这歌就是这个情绪」
的词一样重 —— 跳过一首歌，等于同时否定它所有沾边的情绪。

实测全库 1095 首的词条占比分布：

| 分位 | p25 | p50 | p75 | p90 |
|---|---|---|---|---|
| 词条占比 | 0.208 | **0.291** | 0.421 | 0.570 |

**63.6% 的词条占比 <35%** —— 大多是「蹭到的」。一刀切计票让这些蹭到的词
获得了和主导情绪同等的票重。

### 19.2 改法：票重 = 占比

```
票重 = round(占比 × 100)      // 1~100 票
```

跳过一��� 80% emo / 20% 静谧 的歌 → emo −80 票、静谧 −20 票。主次分明。

**三个关键决定**：

1. **票重用整数（×100），不改表结构** —— `word_preferences.likeVotes/dislikeVotes`
   是 INTEGER；改 REAL 要动 schema、类型和所有判定。整数方案只要**一条迁移把
   历史票 ×100**，让新旧票在同一把尺子上（否则新票 15~100 票会立刻淹没历史的 6 票）。
   归属判定 [WordPreference.kind] 是**相对**比较（喜欢票多 vs 不喜欢票多），
   缩放不改变它。
2. **不设占比门槛** —— 加权本身就压制了「蹭到」的词（15% 的词只值 15 票）。
   而如果卡 35% 门槛，**约 40% 的歌会一个票都投不出去**（3 个词各 30% 时），
   收听结果白学。
3. **消费侧不动** —— 补歌仍是三层硬过滤（喜欢且无不喜欢 → 只有无不喜欢 → 全库）。
   加权后 `kind` 判定本身就更准，过滤自动受益。改成「按票差打分排序」是
   行为层面的更大改动，用户拍板**暂不做**。
4. **跳过判定不动** —— 「<30s 或 <1/4 总时长」保持原样，用户拍板**暂不放宽**。

### 19.3 改动

| 位置 | 改动 |
|---|---|
| `domain/playback/ExplorePlaybackPolicy.kt` | 新增 `VOTE_WEIGHT_SCALE = 100` 与 `voteWeightOf(ratio)` 纯函数 |
| `domain/repository/WordPreferenceRepository.kt` | `recordSongOutcome(words: List<String>, …)` → `recordSongOutcome(votes: Map<String, Int>, …)` |
| `data/.../WordPreferencesRepository.kt` | 按票重累加（票重 0 的词不记录） |
| `feature/player/PlayerRuntime.kt` | 结算时把词条占比换算成票重；票重全为 0 时不记 |
| `data/.../MelodyMigrations.kt` | 新增 `MIGRATION_15_16`：历史票统一 ×100 |
| `data/.../MelodyDatabase.kt` | version 15 → 16 |

### 19.4 数据现状（改造前的真机票）

```
放松 2/6   神圣 2/11   emo 0/3   治愈 2/5
元气 4/11  静谧 2/5    燃 1/5    窒息 0/1   躁 0/2
```

9 个词累计 **49 票**，且**全部偏向 DISLIKE**。两个观察：

- 票数极小 —— 加权的收益要票数积累才体现得出来；
- 全是「不喜欢」倾向 —— 可能确实如此（探索模式里快速划掉是常态），
  也可能是跳过判定偏严。这一项用户拍板**暂不调整**，先看加权计票跑一段的效果。

### 19.5 会不会溢出

票存储是 Kotlin `Int`（Room 列是 SQLite 64 位 INTEGER，但 Kotlin 侧 32 位）：

| | 值 |
|---|---|
| Int 上限 | 2,147,483,647 ≈ 2.1×10⁹ |
| 单次结算最大票 | 5 词 × 100 = **500 票** |
| 撑爆需要 | 2.1×10⁹ / 500 = **430 万次结算**（430 万首歌） |
| 按每天 100 首 | **约 118 年** |

**实际到不了。** 但到那时 `old + weight` 会**静默溢出成负数** → `kind` 判定翻转
（票多者胜变成票少者胜）→ 词条归属无声反转。**这比溢出本身更糟**，
所以加法改成**饱和加法**。

**这里踩了一个坑**：第一版写成 `(old + weight).coerceAtMost(Int.MAX_VALUE)`，
**是假的** —— `Int.MAX_VALUE - 5 + 100` 在 Int 里就溢出了，
之后的 `coerceAtMost` 拦不住一个已经是负数的值（实测漏成 -2147483554）。
必须**用 Long 中间值**：`(base.toLong() + delta).coerceAtMost(Int.MAX_VALUE).toInt()`。
**测试当场抓到了这个**（造一个接近上限的存量票再投一票）——
没有那条测试，我会以为已经防住了。

### 19.6 显示：占比，不是票数

票是「占比 ×100」，绝对值是 15~1500 这种量级，对用户没有意义；
而且票重 15 的歌折算成「1 首歌当量」会显示 0（大部分歌都不到 1）。

改成显示**喜欢票占比**（`WordPreference.likeSharePercent`）——它直接对应判定依据
（票多者胜），也不受刻度影响。NEUTRAL（平票）显示「中立」。

### 19.7 边界

- **用户手动标记的词**占比按 1.0 算（`emotionMatchRatiosOf`），票重 100 ——
  那是用户自己的判断，比模型的更可信。
- **票重 0 的词不记录**：占比 <0.5% 的词不是「这个情绪」，只是碰巧落在附近。
- **历史票迁移是缩放不是清零** —— 用户已有的学习记录保留（相对关系不变）。
  想彻底重来仍可用设置里的「重新探索」（`clearAll`）。

## 20. 探索播放：补歌池「非空即用」的自锁（2026-10-25）

### 20.1 用户报的现象

重新探索后一路点下一首：

1. 只补了 **3 首**「没有情绪分析」的歌（超 20 分钟、分析失败，没做过分析就没有词条）；
2. 再往后切歌**不再补充**；
3. 队列播完**回到第一首**重新循环。

预期是「全库随机 5 首」。

### 20.2 根因：降级判据是「池子非空」，不是「池子够不够补满」

补歌池分三层降级（`PlayerRandomQueueFacade.buildExploreRefillPool`）：

1. 含 ≥1 喜欢词 且 不含不喜欢词；
2. 仅不含不喜欢词；
3. 全库。

原来的判据是「**第 1 层非空就用第 1 层，否则第 2 层非空就用第 2 层**」——
自锁链条由此形成：

1. 用户一路点下一首 → 每首都判「快速跳过」→ 每个词条投**不喜欢**票；
2. 很快所有词条都成了 DISLIKE → 第 1 层空；第 2 层只剩**没有词条的歌**
   （没做过情绪分析的天然「不含任何不喜欢词」）→ 3 首；
3. 第 2 层**非空** → 被采用 → 只补 3 首（**3 < REFILL_COUNT = 5，从来没被检查过**）；
4. 再切歌时这 3 首已在队列里 → 第 2 层空了 → `no more songs outside queue` →
   **永远不再补充**；
5. 队列不再增长 → Media3 的 `REPEAT_MODE_ALL` 在窗口末尾回绕 → **回到第一首**。

第 3 步是根因，第 5 步是它的可见后果。

### 20.2.1 真机库复算：三个池子长什么样

用真机库快照（`live_v16`，1098 首）按 App 的真实投票口径复算：

| 池 | 判据 | 实际首数 |
|---|---|---|
| 池 1 | 含 ≥1 喜欢词 且 不含不喜欢词 | **0** |
| 池 2 | 仅不含不喜欢词 | **3** |
| 池 3 | 全库 | 1098 |

池 2 的那 3 首是 `id=66/67/68` —— **全库唯一 3 首没有情绪分析的歌**
（36 分钟 / 57 分钟 / 27 分钟的长合集）。和用户报的「只补 3 首没有情绪分析、
超过 20 分钟的歌」一字不差。

### 20.2.2 为什么池 2 恰好只有 3 首：偏好表退化成了「拒绝所有有标签的歌」

| | |
|---|---|
| 9 个 auto 组的代表词 | 元气 / 燃 / 神圣 / 治愈 / 静谧 / emo / 躁 / 放松 / 窒息 |
| 偏好表里的 9 个词 | **完全相同** |
| 它们的归属 | **全部 DISLIKE** |

而探索补歌用的词条来自 `emotionMatchRatiosOf` —— **完整分布，不过滤展示门槛，
只要有窗口投过票的组就算一个词条**。于是：

> 任何一个窗口都只会投给 9 个 auto 组之一，而这 9 个组的代表词**全部**是 DISLIKE
> → 「不含不喜欢词」在数学上**等价于「没有任何情绪词条」**
> → 等价于「没做过情绪分析」
> → 池 2 = 全库 3 首没分析过的歌。

所以这不是「模型给某些歌打了奇怪的标签」，而是**偏好系统退化成了
「拒绝所有带标签的歌」**：用户快速划歌 → 每首都投不喜欢 → 所有词都成 DISLIKE
→ 池 1 恒为 0、池 2 恒为 3 首。

**这意味着修复判据之后，探索播放实际走的是池 3（全库随机）** ——
正是用户预期的行为，但也意味着**偏好筛选层在这个用户身上已经没有任何信号**。
要让它重新起作用，得解决上游（跳过判定偏严 / DISLIKE 放大效应），见 §20.5。

### 20.3 改法

- 降级判据从「池子非空」改成「**池子 ≥ REFILL_COUNT(5)**」，不足就降级到下一层，
  最终全库；
- 候选池先**排除已在播放队列里的歌**（原来靠 `planExploreRefill` 内部排除，
  但池子大小是在排除之前算的，判不准）。

现在保证：**只要全库还剩 ≥5 首不在队列里，就一定能补满 5 首。**

### 20.4 测试

新增回归用例 `exploreRefillFallsBackWhenPreferredPoolIsSmallerThanTheRefillCount`：
20 首库、队列已占 10 首、8 首带讨厌词、2 首没词条。

- 旧判据：只补 2 首；
- 新判据：补满 5 首，日志出现 `fall back to full library`。

**验证过它确实抓得住**：把主代码回退到修复前跑单测 → 该用例 FAILED（31 tests, 1 failed）；
恢复修复后 31 tests 全绿。

### 20.5 没动的部分

- **跳过判定不动**（<30s 或 <1/4 总时长就投不喜欢票）—— 用户两次拍板暂不调整。
  本次修的是「池子被判据卡住」这个下游后果，不是上游成因。
- **DISLIKE 的放大效应仍在**：1 次跳过 → 1 个词被排除 → 该词出现在 40% 歌里 →
  40% 歌被排除。可能的更根本修法是给 DISLIKE 加**证据量门槛**（如 ≥3 票才参与排除），
  本轮不做。

## 21. 探索计票：详情页显示 2 个词，跳过却投 6 个（2026-10-25）

### 21.1 用户发现的现象

歌曲详情页只显示 2 个情绪标签；跳过这首歌后，「不喜欢」的词条却有 6 个。

### 21.2 根因：两条路径用了不同口径

| 路径 | 取词口径 | 全库平均 |
|---|---|---|
| 详情页显示 | `emotionTagRatiosOf`：卡 `MIN_RATIO=15%`，最多 `MAX_TAGS=4` | **2.30 个/首** |
| 跳过时计票 | `emotionMatchRatiosOf`：**完整分布**（任何组拿到过 1 窗就算） | **6.26 个/首** |

真机日志实例：

```
explore learn: song=809 skipped=true votes=元气x48,治愈x27,神圣x13,静谧x6,放松x4,窒息x3
```

这歌详情页只显示「元气 / 治愈」，但完整分布里有 6 个组各拿到过窗口 → 6 个词都吃到票
（票重 = 占比×100，所以次要词票少，但**照样记**）。

全库统计：**96.3% 的歌**投票词条比显示的多；**68.8% 的歌**一次跳过就投 ≥6 个词。

### 21.3 这也是「所有词都变不喜欢」的上游

跳过一首歌同时否定 6.26 个词（而不是 2.3 个）→ dislike 扩散速度是应有的 **2.7 倍**
→ 几十首歌内 9 个 auto 组代表词全部染黑 → 补歌池 1 恒为 0、池 2 恒为 3 首
→ 探索播放的偏好筛选层彻底失效（见 §20.2.2）。

### 21.4 改法：计票口径与展示层对齐

| 位置 | 改动 |
|---|---|
| `core/model/EmotionTags.kt` | 新增 `emotionVoteRatiosOf`：卡 `MIN_RATIO` + 最多 `MAX_TAGS`，与展示层同源 |
| `domain/.../ExplorePlaybackPolicy.kt` | 新增 `VOTE_MIN_RATIO` / `VOTE_MAX_TAGS` —— **直接引用** `EmotionGroup.MIN_RATIO` / `MAX_TAGS`，不是抄一份数字，两者不可能漂移；新增纯函数 `votesOf(ratios)` |
| `feature/player/PlayerRuntime.kt` | 拆成两份缓存：`moodEmotionRatiosCache`（完整分布，给时段匹配 + 补歌过滤，**不动**）与 `exploreVoteRatiosCache`（卡门槛，给探索计票）；计票改读后者 |

实测：门槛 15% 时**没有一首歌投不出票**（每首歌至少有一个组 ≥15%），
平均词数 6.26 → **2.31**，正好等于详情页显示数。

### 21.5 没动的部分

- **DISLIKE 证据量门槛不加**（用户拍板）：保持现在的即时反应。
  一次误划仍可能把某个词拉黑 —— 但词被染黑的面积小了 2.7 倍。
- **跳过判定不动**（<30s 或 <1/4 总时长）：用户两次拍板。
- **时段播放匹配不动**：它的 35% 门槛是另一回事（匹配要能找到排第 5 的目标词）。
- **补歌过滤仍用完整分布**：与计票口径不同是有意的 —— 过滤是「排除含讨厌词的歌」，
  计票是「学你不喜欢什么」。

### 21.6 历史票是旧规则学到的

现存 dislike 票是在「每首摊到 6.26 个词」的旧规则下累计的，**系统性偏多**。
要恢复偏好层，请在 设置 → 随心播放增强 → 词条偏好 → 「重新探索」清一次历史票。
