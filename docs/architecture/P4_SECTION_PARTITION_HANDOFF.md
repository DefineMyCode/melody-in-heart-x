# P4 交付说明：L2 页面分区化（我的页）

日期：2026-09-29　分支：`plugin-ui`　状态：**已完成，真机验收通过**
设计文档：`docs/architecture/PLUGIN_SHELL_DESIGN.md`
前置：`P1_SKIN_MODEL_HANDOFF.md`、`P2_NAV_SHELL_HANDOFF.md`、`P3_PLAYER_SHEET_HANDOFF.md`

## 一、范围（按用户裁定收窄）

P4 原计划 = L2 分区化 + L3 行模板/网格 + L4 播放页形态可配。

**本阶段只做 L2，且只做「我的」页。** 依据是实施前与用户对齐的结论：

- L2 的**收益尚未验证**——原型里两套皮肤的差异主要来自 L1（导航外壳）与 L3（行模板），
  页面内部重排的差异感有多少是未知数（方案D 式返工风险）；
- 曲库页 838 行、牵连四套子视图与多个对话框，值得先在低风险页面上把机制验通；
- 能力上限按 **B 级** 做（裁剪 + 重排），**不做 C 级**（改每个分区的长相）。

**C 级刻意留成增量路线**：不给零件"开洞"加参数，而是**用到时再加一个零件**
（如「播放统计·简洁」）。这样成本从"提前实现 N×M 种组合"降到"用一个做一个"。

---

## 二、做了什么

| 交付 | 说明 |
|---|---|
| `feature/user/UserSections.kt` | 我的页分区 key 常量 + `DEFAULT_ORDER`（= 改造前写死顺序）+ 容错解析 |
| `UserScreen.sectionOrder` 参数 | 按传入顺序渲染分区；**默认值 = 改造前顺序，故不传时零变化** |
| `AppShell.myPageSectionOrder` | 描述解析出的分区顺序；空 = 未指定，页面回落默认 |
| `SkinShellResolver.resolveMyPageSectionOrder` | 从 `pages.me.sections` 提取 part 名并过滤为页面认识的 key |
| 零件库登记 5 个分区 | `userInfo` / `playStats` / `moodTimeSlot` / `emotionScan` / `fileCheck` |
| `DefaultSkin` 描述更新 | 我的页从单个 `myOverview` 拆成 5 个显式分区 |

**改动极小**：我的页的 5 个 section 本来就已经是独立 Composable，
所以 L2 在这里主要是"接线 + 提 key"，没有大拆。

## 三、★ 顺带修掉一个真实保真 bug（P1 遗留）

做 L2 前先回源码核对，发现 **P1 的描述与代码事实不符**：
`DefaultSkin` 声称曲库有 5 个分段「歌单/歌手/专辑/情绪/歌曲」，
但 `LibraryTab` enum 只有 **4 项**——「歌曲」是**歌手/专辑详情页**的子标签，不属于曲库页。

**为什么一直没被发现**：P1 那条测试是**拿描述自证描述**（expected 抄自原型草案、
actual 来自 `DefaultSkin` 自身），两边同源，于是完美地把错误锁死、测试全绿。
这与 P2 的 `startPage` 是同一类问题（描述 ≠ 代码事实），但更隐蔽。

**已修**（见 commit `b50cff6`），并新增 `LibrarySegmentsMatchSourceTest`
**直接读源码**解析 `LibraryTab` 做对照。

## 四、防复发：本阶段新增的两条"对照源码"测试

P4 的核心方法论收获：**描述与代码事实之间必须有测试绑定，不能靠描述自证。**

| 测试 | 在防什么 |
|---|---|
| `LibrarySegmentsMatchSourceTest`（core/skin，4 条） | 曲库分段描述 ↔ `LibraryTab` 源码 |
| `UserSectionsTest`（feature/user，10 条） | 我的页分区 key ↔ 描述里的 part 名；默认顺序 ↔ 改造前写死顺序 |

**两条都做了负向对照验证**（证明它们真在读源码，不是又一个自证）：

- 往 `LibraryTab` 注入第 5 项 `SONGS("歌曲")` → 3 条失败；还原后恢复全绿；
- 从描述删掉 `fileCheck` → 1 条失败；还原后恢复全绿。

## 五、真机验收（已通过）

模拟器（tfl_smoke / API 36 / x86_64）：

| 验收项 | 结果 |
|---|---|
| **默认骨架：我的页与改造前逐卡一致** | ✅ 头像区 → 播放统计 → 随心播放增强 → 情绪分析 → 文件校验（5 张，顺序不变） |
| **默认骨架：底栏 3 Tab** | ✅ 曲库 / 播放 / 我的 |
| **抽屉型骨架：分区被裁剪** | ✅ 我的页只剩 **3 张**（`userInfo` / `playStats` / `emotionScan`），**随心播放增强与文件校验被删掉** |
| **抽屉型骨架：底栏 2 Tab** | ✅ 曲库 / 我的 |
| 崩溃 / 卡死 | ✅ 零崩溃 |

**这组对照正是 P4 要证明的能力**：同一份页面实现，被两份描述渲染成不同的卡片集合——
"删掉某张卡"从"改代码重发包"变成"改描述"。

## 六、本阶段**没有**做的事

- **曲库页分区化**。它的 4 套子视图（歌单/歌手/专辑/情绪）与多个对话框耦合更深，
  838 行。机制已在"我的"页验通，可按同一模式推进。
- **L3 行模板/网格**（`songList` 的 `template` 已能表达、校验器已支持，但尚未接线到渲染）。
- **L4 播放页形态可配**（`nowPlaying.coverShape` 等字段已能表达，未接线）。
- **L5 资源包**（P5）。
- **C 级能力**（改分区长相）——按裁定走"用到时再加零件"的增量路线。

---

## 七、下一步建议

**给用户看这一步的效果再决定是否继续投 L2。**

预期要回答的问题：**「我的」页裁掉两张卡之后，差异感是否明显？**

- 若明显 → 按同模式推进曲库页分区化，然后做 L3/L4；
- 若不明显 → L2 的价值可能有限，应把力气转到 **L3（行模板/网格）** 与
  **L4（播放页形态）**——原型里这两层贡献的差异感更大。

这与我实施前建议的走法一致：先小成本验收益，避免在全量投入后才发现"看着没差别"。
