# 心乐零件库原型 —— 同一套零件拼出三种骨架

**入口**：`parts-library.html`
**URL**：http://85.137.246.39:4311/mihx-plugin-shell/parts-library.html

## 这份原型要回答什么

上一轮已确认：插件方案从「代码插件」转向 **路线B（声明式结构 + 零件库）**。
但路线B 唯一的软肋是——**零件库够不够丰富**。零件太少，皮肤只能换皮（就是你已经
嫌弃过的「跟原版没差别」）；零件够，才能像另一个 App。

这份原型把这件事做成**可验证的**：三套差异极大的骨架，**全部由同一份零件库渲染**，
只换数据描述、不换一行渲染代码。你能一眼看出零件库缺什么。

## 三套皮肤（切换即证）

| 皮肤 | 结构 | 在验证什么 |

## 右侧四块面板（都是给你拍板用的）

**① 选皮肤描述** —— 切换三套骨架，主体区即时重渲。

**② 零件覆盖度表** —— **从三份描述里自动统计**，不是手写的。看「覆盖率」列：
- `3/3` 绿色 = 通用零件（换骨架也用得上，值得投入）
- `1/3` 橙色 = **骨架专属零件**（换骨架就用不上，是负债）

这张表就是「零件库该扩到哪」的直接依据。

**③ 三个滑条** —— 容器填充 / 圆角 / 描边粗细。这是本原型最重要的一个发现：
**已实测的色板（`THEMES`）改不出差异感**——心乐墨色 `#121212` vs 网易云深色 `#1A1A1A`
只差 8 级灰，没人分得出来。真正区分「心乐（零实心块）」与「网易云（卡片墙）」的
是这三个值。所以它们必须是令牌，而不是写死在页面里。

**④ 皮肤 JSON** —— 就是插件包要交的那「一个文件」。可离线分享、导入时能逐字段校验
并给出精确失败原因（未知零件名 / 版本不符 / 字段越界）。皮肤里没有任何可执行代码，
所以组合期零崩溃风险。

## 已知边界（别误读这份原型）

- **表现层极限没被压测**：黑胶转盘实现了，但频谱、波形进度、轮播、无限流首页等
  第 6 层零件**刻意没做**——它们每个都要独立开发，是「零件库该扩到哪」需要你拍板的部分。
- 皮肤是**数据**不是代码：本原型里的 `SKINS` 对象就是真实插件包的内容契约草案，
  但字段名与最终 `schemaVersion` 仍需按 `docs/architecture/PLUGIN_SHELL_DESIGN.md` 定稿。
- 上一轮的 `skeleton-a/b/c-*.html` 是**抽屉交互形态**的对比（peek/全屏/形变），
  与本文件的「零件库覆盖度」是两件不同的事，都保留。
