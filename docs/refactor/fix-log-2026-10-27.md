## 第二轮补做（按「用户可感知」重新排序后追加的五项）

第一轮完成后按**用户可感知程度**重新排了优先级，发现第一轮漏掉了几项**用户真能看见**的问题。追加修复如下：

### ✅ M-9 封面缓存：非原子落盘 + 同哈希并发重复劳动

**用户症状**：封面显示成半张 / 空白图，**且永不自愈**（截断的 JPEG 被缓存住）；
同一专辑 N 首歌重复解码 + 压缩 + 覆写同一文件 → 导入变慢。

- **原子落盘**：先写 `art_<hash>.jpg.tmp` 再 `renameTo`（同文件系统内 rename 是原子的）——
  读者要么看到旧文件、要么看到**完整**文件，不会看到写了一半的。
- **同哈希去重**：`ReentrantLock` + `Condition` 维护「正在写的哈希」集合，
  同一哈希只允许一个线程解码/压缩/落盘，其余线程等它完成后直接复用产物；
  等不到（对方卡住）就自己写 —— 并发写现在也是安全的（原子 rename）。
- **回归测试** `AlbumArtExtractorCacheTest`：8 线程并发取同一张封面 →
  断言 `cacheWriteCount == 1`（只写了一次）、目录里无残留 `.tmp`、
  且落盘文件**可完整解码**（这条直接锁住「读者不会看到半张图」）。

### ✅ M-23 情绪 upsert 的 TOCTOU：用户校准会被静默覆盖

**用户症状**：手动标的情绪词条**无声消失**，用户不知道为什么。

- 原实现「读旧行 → 内存合并 userTags → 整行 upsert」有窗口：用户恰在那一瞬间保存校准，
  扫描随后用**陈旧的** userTags 覆写回去。
- 现在把合并规则搬进 SQL 的 `CASE` 表达式，**一条 UPDATE 完成**：
  新值带词条 → 用新值；新值不带 → 保留行上已有的。无论校准落在读前还是读后都不丢。
- 顺带修掉 `saveCorrection` 的 check-then-act：原先「查时无行、查后扫描写入」会走
  `upsertUserOnlyCorrection`（`@Upsert` 整行替换）→ **把分析结果擦掉**。
  现在改成「先原子 UPDATE，没命中再 `INSERT OR IGNORE`」，两条路径各自原子。
- **回归测试** `SongEmotionsRepositoryTest` +3 例（真实 Room）：
  重扫不吞校准 / 新值带词条时以新值为准 / 未分析歌曲的 user-only 行不会被后续分析擦掉。

### ✅ M-12 「已在歌单」判定 O(歌数 × 歌单歌曲数)

**用户症状**：往大歌单批量加歌时，弹窗**滚动/打字掉帧**。

- `songs.count { it.id in playlist.songIds }` 里 `songIds` 是 List，`in` 是线性扫描；
  批量加 300 首到 2000 首的歌单 = 每个歌单行 60 万次比较，屏幕上 10 个歌单 = 600 万次/帧，
  而且**未 memoize**（每次重组重算）。
- 现在两侧都转 `Set`（歌单 id 集合按 `playlist.songIds` 记忆化），判定 O(1)。

### ✅ M-14 Home 屏每秒重组 5 次 → 只剩进度条那一小块

**用户症状**：后台耗电与发热；Home 屏整棵子树（含 31 参数的 `SongInfoSection`）跟着播放进度重算。

- 播放位置窄流原先在 `NowPlayingSurface` 顶层订阅，每 200ms 一个新值经
  `HomeRouteState` → `HomeScreen` → `SongInfoSection` 一路传下去 → **整棵子树每秒重组 5 次**。
- 现在把**窄流本身**传下去，由新抽出的叶子组件 `PlaybackProgressBar` 内部订阅 ——
  重组范围收缩到滑杆 + 两个时间标签这一小块。
- 顺带修掉拖动状态未按歌曲 id 复位的问题（换歌时旧歌的拖动位置会被带进新歌）。

### ✅ M-18 Route 边界形同虚设 → 路由真的能跳过重组

- 全由函数类型构成的 `*RouteActions` 被 Compose 推断为 **unstable** →
  `Route(state, actions, …)` 永远无法跳过。**15 个 Route Actions 类统一补上 `@Stable`**。
- `HomeRoute` 里包装出来的 lambda（toast 等）改用 `remember` 固定身份。
- `NowPlayingSurface` 里 `HomeRouteState` / `HomeRouteActions` 的实例改用 `remember` 构建，
  身份稳定 → Route 边界第一次真正具备跳过重组的能力。

**双层兜底**：

1. **实现侧下沉**（主修复）— `data/.../repository/MediaMetadataRepository.kt`

2. **调用侧统一**（纵深防御）— 新增 `core:ui` 的 `loadSongInfoSafely(loadSongInfo, song)`，
   7 处裸调点（PlaylistScreen / LocalMusicManagementView / AlbumDetailScreen /
   ArtistDetailScreen / EmotionLibraryView / VersionManagementScreen / VersionComparisonScreen）
   与 app 壳层那处一起改为走它。`CancellationException` 同样原样上抛。

### ✅ M-22 两处读改写丢更新 → SQL 级原子

| 位置 | 旧实现 | 新实现 |
|------|--------|--------|
| `QuickSkipSongsRepository.incrementShortPlayCount` | 读 count → +1 → 整行 upsert | `ensureQuickSkipShortPlay`（`INSERT OR IGNORE`）+ `incrementQuickSkipShortPlay`（`UPDATE … SET count = MIN(count + 1, 2147483647)`） |
| `WordPreferencesRepository.recordSongOutcome` | 读整表 → 算新票 → 整表 upsert | `ensureWordPreference` + `addWordVotesDelta`（`UPDATE … SET likeVotes = MIN(likeVotes + :delta, 2147483647)`） |

**为什么不用 `INSERT … ON CONFLICT DO UPDATE`**（UPSERT）：该语法要 SQLite ≥ 3.24，
而本项目 JVM 测试环境的 SQLite 影子实现不支持（实测报 `near "ON": syntax error`）。
改成「幂等建行 + 语句级原子 UPDATE」两步后在**任何** SQLite 版本上都能跑，
且同样无 lost update —— 每次调用先 ensure（行不存在则建，已存在则忽略）再自增，
保证自增时行一定存在；自增语句本身是 SQL 级原子的。

**新增回归测试** `data/src/test/.../AtomicIncrementRoomTest.kt`（**真实 Room 内存库 + 真实并发**）：
50 个并发自增后计数必须正好是 50；喜欢/不喜欢两列分别累加互不干扰。
旧实现在这两个测试下会得到个位数。

### ✅ M-19 日志脱敏每次调用编译 6 个 `Regex`

`core/common/.../AppLogger.kt`：6 个模式提到文件级 `private val`，各编译一次。
（已核查：6 个模式均无嵌套量词、lookbehind 定宽，**不存在灾难性回溯风险**。）

### ✅ M-20 `PerformanceTrace` release 白名单形同虚设

根因：`allow()` 只决定「是否计算」，输出仍走 `AppLog.info` → `AndroidAppLogger.info`
→ 被 `debugLoggingEnabled`（= `BuildConfig.DEBUG`）拦住 → release 下一条都出不来；
且 `allow()` 全项目零调用点。

**修法**：给 `AppLogger` 增加独立的 `performance(tag, message)` 通道
（`AndroidAppLogger` 用独立的 `performanceLoggingEnabled` 开关，**不受 debug 开关约束**），
`PerformanceTrace.log` 改走该通道。`MelodyApplication` / `LoggerModule` 显式打开
`performanceLoggingEnabled = true`（release 也要开 —— 白名单的价值正在于此）。

**新增回归测试** `PerformanceTraceTest`：断言 allowlisted 操作**确实抵达性能通道**，
且未白名单时**连 metadata 都不构造**。

### ✅ N-1 `PlaybackStateStore` 5 处 `runBlocking` → 挂起化

`domain` 的 `PlaybackStateStorage` / `PlaybackStateRepository` / `PlaybackRestorer` 全部挂起化，
`:player` 的 `PlaybackStateStore` 去掉全部 `runBlocking(Dispatchers.IO)`。

**顺序保证**：原先「清空快照」是同步阻塞、「写快照」是异步，两者混用时序靠
「同步那个先跑完」保证。全异步化后若都挂到多线程 `Dispatchers.IO` 上，顺序不再保证
（可能出现「快照刚写完又被清掉」）。因此 `PlayerPersistenceGraph` 引入
**通道 + 单消费者**的 FIFO 持久化队列（不用 `limitedParallelism(1)` ——
`Dispatchers.Unconfined` 不支持它，测试会炸）：

- 清空与写入走同一条队列 → 顺序得到保证；
- 该队列**不挂在 ViewModel 生命周期上** → `onCleared` 排队的最后一次写入仍能落盘
  （上一轮「有意保留 runBlocking」的理由是「改异步有丢状态风险」，现在用保活队列解决了）。

**行为变化（如实记录）**：`onCleared` 的最终落盘从「阻塞主线程直到写完」变为「排队写入」。
最坏情况下进程被立即杀死会丢掉最后 5 秒内的进度（autosaver 每 5s 已落盘一次），
换来的是主线程不再有 DataStore 磁盘写的阻塞点。

## 第二波（情绪链路性能收敛）

本轮新功能域（情绪分析）贡献了 23 条 Major 中的 8 条，且互为因果，整体收敛：

```
批扫逐首写入 → Room 整表重发 → 全库曲线 JSON 重解析 → 同一条曲线投票 3~4 遍
                                                    ↓
                                        探索补歌池对全库做 3 遍词条派生
```

| 条目 | 修法 |
|------|------|
| **M-1** 情绪表整表重发 + 全量曲线重解析 | `SongEmotionsRepository` 加**已解析曲线缓存**（键 = songId + analyzedAt）：行未变则复用，**每次重发只有新写入的那一行需要解析**。30 万次解析 → 300 次 |
| **M-3** 扫描状态页每 2 秒拉两次全表 | 新增聚合查询 `emotionTableStat()`（行数 + 最近分析时间）与 `emotionRecentAnalyzedTimestamps(20)`，轮询成本从 O(库大小) 降到 O(1) |
| **M-4** 探索补歌池对全库做 3 遍词条派生 | `buildExploreRefillPool` 一次派生（`tagsBySong`）全程复用；`moodEmotionTagsOf` 类型由 `List<String>` 改为 `Set<String>`，直接透传缓存的 key 视图，**零分配** |
| **M-13** `Song.parsedArtists` 是每次重算的 getter | 改为构造期算一次并缓存（`private val` 不参与 data class 的 equals/hashCode/copy 契约） |
| **M-11** 情绪展示区同一条曲线投票 3~4 遍 + 逐帧扫描 | 新增 `core/model/EmotionDisplay.kt`：**只投票一次**，三处结论（词条 / 占比 / 把握档位）全部从同一份投票派生；`EmotionGroup.voteRatios` 把循环不变量（候选组、锚点）提到循环外，循环内零分配；`hasSignificantPeak` / `smoothCurve` 提到组合期并 `remember`；虚线 `PathEffect` 提为文件级常量 |
| **M-2** 批扫 Worker 每首歌复制整份曲库 + 逐首读 DataStore | 新增 `SongRepository.containsSong(songId)`（**无分配的 O(n) 判定**，不再 `songs.toList()` 整库拷贝）；暂停标志改为**订阅一次、循环内读内存**（原为每首一次 DataStore 磁盘读） |
| **M-5 / M-6** 缺索引 + 事件表永不清理 | 新增 `index_songs_albumId`、`index_playback_events_songId`（迁移 16→17，`MIGRATION_16_17`）；`playback_events` 加**保留策略**（12 个月，每次落盘时清理） |
| **M-7** 启动恢复把 `songs` 表物化 3 遍 | 实体只读一次；albumId 映射改用只取两列的 `songAlbumIds()` |

> **M-7 的一个坑（已由测试抓出）**：`syncLibraryCatalog` 会**重建专辑目录并把 albumId
> 回写到 songs 表**，所以 albumId 必须在它**之后**重新读 —— 原先第二次 `dao.songs()`
> 不是冗余调用。改窄查询时若直接从首次加载的实体派生，albumId 会全为 null
> （`MusicRepositoryRoomTest.loadSongsSyncsArtistAndAlbumCatalog` 立刻失败）。最终形态是
> 「首次读全部列 + 目录同步后只补读 id/albumId 两列」。

## 第四波（播放器音频链路：系统空间音频 / 杜比内容）

> 起因：评审后的专项追问「安卓设备系统自带的音效（如杜比全景声）跟本 App 适配吗？
> 什么都不配置时是什么效果」。结论：**系统音效通路本来就是适配的**
> （`USAGE_MEDIA` + `CONTENT_TYPE_MUSIC` + 平台默认 `SPATIALIZATION_BEHAVIOR_AUTO`，
> 正是 Android 空间音频的判定条件），**杜比 Atmos「内容」则会被 FFmpeg 扩展降级**。
> 本波修的是后者。

### ✅ 渲染器模式 PREFER → ON：让杜比内容走设备原生解码器

| | 旧（PREFER） | 新（ON） |
|---|---|---|
| 渲染器顺序 | FFmpeg 扩展在前，平台 MediaCodec 在后 | 平台 MediaCodec 在前，FFmpeg 扩展兜底 |
| `audio/eac3-joc`（DD+ Atmos） | FFmpeg `ff_eac3_decoder` → 只出基础 5.1，**JOC 对象层丢弃** | 平台 `audio/eac3` 解码器（杜比 Atmos 渲染器）→ **Atmos 成立** |
| `audio/ac4` | 同上 | 平台 AC-4 解码器 → Atmos 成立 |
| `audio/true-hd`（TrueHD Atmos） | 同上 | 平台解码器（有则生效） |
| WMA / APE | FFmpeg 扩展 | 平台无解码器 → 仍由扩展兜底（**无变化**） |

Media3 1.9 的常量名是 `EXTENSION_RENDERER_MODE_ON`（**没有**旧版 ExoPlayer 的 `USE`）；
`ON` = 平台解码器优先、扩展追加在后。它与 `PREFER` 的差别就是渲染器列表里的插入位置
（字节码：mode==PREFER 时扩展插在 `size-1`，即平台渲染器**之前**；否则追加到**末尾**）。

平台侧能接住 JOC 的关键：Media3 的 `MediaCodecUtil.getAlternativeCodecMimeType()`
把 `audio/eac3-joc` 映射到 `audio/eac3`，于是命中设备的杜比解码器。

### ✅ ALAC 用 selector 排除回 FFmpeg（保住 2026-08-31 的规避措施）

渲染器改平台优先会**连带改变 ALAC 的解码器归属** —— 而 ALAC 正是真机 SIGSEGV
（2026-08-31，小米高通 `c2.qti.alac.sw.decoder`）的当事格式，当年验证过的规避手段
就是「ALAC 等轨优先命中 FFmpeg 扩展解码器，根本不经厂商软解」。

新增 `MimeExcludingMediaCodecSelector`（`:player`）：把指定 mime 从平台解码器候选里剔除。
Media3 的 `MediaCodecAudioRenderer.supportsFormat()` 用选择器查候选，**候选为空即判定
不支持**，该 mime 便落到列表靠后的 FFmpeg 扩展渲染器上。

- 排除集：`audio/alac` + `audio/x-lg-alac`。
- 仅在 `FfmpegLibraryProbe.available` 为真时才排除 —— 否则 ALAC 会既没有平台解码器
  也没有扩展解码器，直接播不了。
- 失败模式安全：即便选择器因任何原因不生效，结果只是退回「平台优先」的默认行为，
  不会让音频彻底无解码器可用。

**新增回归测试** `MimeExcludingMediaCodecSelectorTest`（5 例）：被排除的 mime 返回空候选
且**不触碰** delegate；未排除的 mime 原样委派且参数一致；排除是精确匹配
（`audio/alac-extra` 不被误伤）。

### ✅ 关闭浮点输出（附一条**实测澄清**：它与空间音频无关）

`setEnableAudioFloatOutput(false)`。过程中把 Media3 1.9 的相关字节码逐条核实过，
结论与最初的推测**不同**，如实记录：

- `DefaultAudioSink.shouldUseFloatOutput(enc) = enableFloatOutput && Util.isEncodingHighResolutionPcm(enc)`，
  而 `isEncodingHighResolutionPcm` 只认 24bit / 32bit（含大端）与 **float**，
  **不含 16bit** → 平台 MediaCodec 解出的 16bit PCM 本来就不走浮点，**开关无影响**。
- Media3 只有 `ToFloatPcmAudioProcessor`、**没有 float→int16 的反向处理器** →
  FFmpeg 扩展解出的 float **无法**被降级成 16bit，AudioTrack 仍是 float。
  ⇒ 关闭浮点输出**不可能**让 FFmpeg 路径变成 16bit，也就不可能改变空间音频判定结果
  （Android `Spatializer` 只接受 `PCM_16BIT`）。
- 该开关真实的作用面：仅 24/32bit PCM 源（罕见）从「升级成 float」变为「保持整数 PCM」。

所以本项是**兼容性收口**（避免个别 ROM 上 float AudioTrack 的问题），
**不是**空间音频的修复手段 —— 真机上验证空间音频是否生效，仍应按官方文档用
`adb shell dumpsys audio` 看 `mHasSpatializerEffect` / `isSpatializerEnabled`。

### 尚未解决（需要单独一轮）

- **格式白名单仍挡着杜比文件**：`AudioFileUtils.AUDIO_EXTENSIONS` 只有
  `mp3 flac wav m4a ogg aac opus wma ape`，没有 `ac3/eac3/ac4/m4b/mka/mkv`；
  且 `isAudioFile` 的 mime 分支实际不生效（SAF 扫描传 `null`，真实路径扫描传
  `java.io.File.type`，在 Android 上恒为 `""`）→ **只按扩展名过滤**。
  ⇒ 渲染器改完之后，杜比文件仍导不进来；这一步要动 Room 数据与 `MediaMetadataRetriever`
  的容器支持度，属独立一轮。
- **立体声默认不被空间化**：Android 平台默认只对多声道内容做空间化（OEM 可自定义），
  所以普通立体声 FLAC/MP3 即便开了「空间音频」通常也原样出声 —— 这是平台行为，不是本 App 的问题。

## 第五波（专辑封面跨进程可读：修 SystemUI 的 FileNotFoundException）

> 来源：真机启动→播放日志（OPPO / ColorOS / Android 14）里 30 条
> `MediaDataManager E Unable to load bitmap` + `FileNotFoundException`，
> **全部来自 `com.android.systemui` 进程**（不是 App 自己），而**歌曲照常播放**。

### 根因（不是新问题，是 8 月那次大重构埋的）

平台的 `MediaSessionRecord.sanitizeMediaMetadata()` 对 MediaSession 元数据里的 artwork URI
**只处理 `content://`**，`file://` 被直接 `continue` 跳过、**不做任何 URI 授权共享**：

```java
if (!ContentResolver.SCHEME_CONTENT.equals(uri.getScheme())) {
    continue;                       // ← file:// 直接跳过
}
mUgmInternal.checkGrantUriPermission(...);   // ← 只有 content:// 才走平台授权共享
```

于是 `file://` 形态的封面 URI 被原样透传给各控制器（SystemUI 媒体控制卡片 / 通知栏 /
Android Auto / 车机），而这些进程读不到 App 私有目录 → 封面加载失败。
**与 Media3 官方 issue androidx/media#271 描述的症状逐字相同**（`MediaDataManager throws a
FileNotFoundException`）。

**这不是新问题**：`b2d6e82`（2026-08-02）的最初实现**就带 FileProvider**——
`artwork_file_paths.xml` + manifest 的 provider 节点，接口注释明写
*"returns a `content://` URI that both Coil (in-app UI) and Media3 (lock-screen / notification)
can load across processes"*。`53269d3 废弃`（2026-08-03，**次日**）把旧单模块 App 整体废弃时，
连同 provider / paths / `ArtworkStore` 一起删掉了；后续重建封面功能时**只搬回了「缓存文件」
这一半，丢掉了「跨进程可读」这一半**，封面遂退回 `file://` 私有路径。

### 修法：恢复被丢掉的那一半

| 改动 | 位置 |
|------|------|
| 新增 `:data` 的 manifest（provider 声明）+ `res/xml/artwork_file_paths.xml`（`<cache-path name="album_art" path="album_art"/>`） | `data/src/main/AndroidManifest.xml`、`data/src/main/res/xml/artwork_file_paths.xml` |
| 新增 `AlbumArtProvider`：本地缓存文件 ↔ `content://` URI 双向映射 + 旧 `file://` 识别 | `data/.../util/AlbumArtProvider.kt` |
| 封面产出改 `content://`（FileProvider 不可用时退回 `file://` 并记 warning） | `data/.../util/AlbumArtExtractor.kt` |
| `refreshAlbumArtIfNeeded` 改三分支：provider URI（查文件）/ 旧 `file://`（在则零重解码迁移，不在则摘掉悬空 URI）/ 其它 URI（MediaStore albumart 原样返回） | 同上 |
| **存量迁移**：Room 恢复后立即把旧 `file://` 改写成 `content://` 并落库 | `data/.../repository/MusicRepository.kt` |

- **authority 用 `${applicationId}.artworkprovider`**，不照抄原始实现的硬编码
  `cn.com.dcsgo.mihx.artworkprovider` —— debug 变体的 applicationId 是 `<pkg>.debug`，
  硬编码会导致变体找不到 provider（已核对合并后 manifest 解析为
  `cn.com.dcsgo.mihx.debug.artworkprovider`）。
- **存量迁移必须发生在恢复播放之前**：恢复流程用内存里的 Song 构造 MediaItem，
  若不改，本次会话发布给 MediaSession 的仍是旧 URI，SystemUI 会持续报错到下次启动。
- **跨进程读权限必须由 App 显式授予**（真机日志修正了最初「平台会自动授权共享」的判断）：
  平台的 `MediaSessionRecord.sanitizeMediaMetadata()` 对 artwork URI 只做**校验**
  （`checkGrantUriPermission`），**不负责授权**；AOSP 侧通篇没有对 artwork URI 的
  `grantUriPermission` 调用。缺这一步时跨进程消费方拿到的是
  `SecurityException: Permission Denial: reading ... requires the provider be exported,
  or grantUriPermission()`。
  授权逻辑收敛到 `:core:common` 的 `ArtworkUriAccess`（共享 helper），**两个调用点缺一不可**：
  | 调用点 | 位置 | 覆盖的对象 |
  |--------|------|-----------|
  | **铸造时** | `:data` `AlbumArtProvider.toProviderUri()` | 新落地的封面（导入期完成，不占播放路径） |
  | **发布时** | `:player` `PlaybackController` 下发 `setMediaItems`/`addMediaItems` **之前** | **存量 URI**（本进程没铸造过、来自上一次运行写进 Room 的）—— 只靠铸造时授权覆盖不到它们 |
  发布时的授权**必须早于 metadata 推送**：跨进程消费方一收到推送就会去读封面，
  等 `onMediaItemTransition` 再授权就晚了（读取先于授权 → 首帧封面空白）。
  授权目标 `com.android.systemui`（媒体控制卡片）+ `android`（框架包）—— 两者在 AOSP 上
  都是 uid 1000(system)，平台媒体通知也在 system_server(uid 1000) 里构建封面，
  一次授权同时覆盖两处。按 URI 去重：同一专辑的 N 首歌共享同一张内容哈希封面 → 一次授权。
  只授权**自家 provider** 的 URI：MediaStore 的 albumart 本来就能跨进程读，授权它既无意义，
  又可能因「非本 App 拥有的 provider」触发 SecurityException 噪音。

> **一次真机验证纠正了「严重性」判断**：改动前后，**通知栏/控制中心的媒体卡片一直都能正常
> 显示封面**——因为 Media3 的 `MediaSessionImpl` 内置 `BitmapLoader`，**在 App 进程里把封面
> 解码成 Bitmap 直接塞进 MediaMetadata 走 IPC**，控制器拿的是位图、根本不需要读我们的 URI。
> MIUI 的 `MediaDataManager` 是额外多走的一条冗余路径，失败后回退到已有位图。
> ⇒ 那批 E 日志是**日志噪音级**问题，不影响功能；本波改动的价值在于让 URI 真正跨进程可用
> （将来接车机 / Android Auto / 第三方控制中心时不必返工）并清掉日志噪音。
- **封面缓存仍留在 `cacheDir`**：搬到 `filesDir` **不能**解决跨进程可读性（filesDir 同样是
  App 私有目录），只会让缓存无限增长（系统不再自动清理），还得自己加 LRU 淘汰。
  当前 `cacheDir` + `refreshAllAlbumArt` 的自愈已够用。

### 新增回归测试

- `ArtworkUriAccessTest`（`:data` 的测试源集，7 例）：自家 `content://` 被授权、
  同一 URI 只授权一次、不同 URI 独立授权、null 忽略、**他家 `content://`（MediaStore）
  忽略**、`file://` 忽略、批量授权去重。
  （放在 `:data` 而非 `:core:common`：Robolectric 只在已收录依赖校验的模块里可用——
  给 `:core:common` 加 Robolectric 会触发 dependency verification 失败。）
- `AlbumArtProviderTest`（10 例）：provider URI 的 scheme/authority、URI ↔ 文件往返映射、
  MediaStore 的 albumart URI **不被**误映射为本地文件、旧 `file://` 在自家缓存目录内**被**识别 /
  目录外**被拒绝**、文件已消失的旧 `file://` 仍能被识别（交由调用方摘掉悬空 URI）、
  铸造 URI 会触发跨进程授权。

> **环境坑（已踩）**：androidx.core 的 `FileProvider` 用静态 `sCache` 缓存
> 「authority → 根目录」映射，而 Robolectric 每条用例都是独立临时目录 ——
> 缓存一旦被上一条用例写入，后续用例的 `getUriForFile` 就会抛
> `Failed to find configured root`。测试需在 `@Before` 反射清掉 `sCache`。
